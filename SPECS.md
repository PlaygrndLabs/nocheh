<area name="Nocheh">

- Nocheh is a personal AI brain. Owned source data, useful memory, and reasoning are the product. Telegram is an adapter; Hermes is the first replaceable runtime. Memory is swappable too; Honcho is the current long-term memory.
- Nocheh owns its dashboard, CLI, archive and files, source identities, audience policy, guarding, approvals, and integration lifecycle.
- Nocheh learns from permitted sources, organizes knowledge, prepares changes, and explains its work under clear owner supervision. Projects are optional aids to understanding. The agent manages routine work within explicit owner authority; the owner can inspect results and decide exceptions through ordinary private conversation and the dashboard.
- Dependable answers are more important than speed. Answer dependability is evaluated separately from response time.

<area name="Foundation and deployment">

- Nocheh uses TypeScript services, React, npm for dependency management and project scripts, and thin Python integration with Hermes. Tested upstream revisions and dependency versions are pinned.
- Hermes and Honcho are Nocheh's harness, and Nocheh does not rebuild what they provide ("dont create wheel again"): where Hermes or Honcho has a built-in feature, Nocheh uses it and keeps no code of its own that duplicates it. Nocheh keeps its own safety layer around them: the secret check, audience and access filtering, and archive provenance.
- Local Docker Compose is the supported development, unattended operation, and acceptance environment. Each installation has one Compose project containing all services, including the owner dashboard and executor.
- Several workspaces run on one machine ("i need multi install to able setup nocheh for more workspaces, personal, companies"). A workspace is one installation in its own folder, with its own `.env`, data, memory, password, Telegram bot, dashboard and backups; workspaces share no data. Its short name is set at setup; renaming a stopped workspace keeps its data ("my current will be name test/dev"). Its Compose project, internal networks, volumes, images, ports, off-site backup folder and dashboard sign-in follow from the name, and `personal` keeps the original `nocheh` names. Setup refuses a name, port, Telegram bot, mini app address or tunnel that another workspace on the machine uses. One command updates every workspace, or one at a time. The setup guide shows the Docker address-pool setting that several stacks need.
- Nocheh provides an exact-revision app deployment script and agent skill for an existing local Docker Compose installation and an existing VPS checkout. A read-only plan identifies the target; an explicit apply verifies checkout ownership and revision, deploys the app service, and checks health. Credentials and runtime state remain in their installation. Deployment is separate from live acceptance and release.
- Agent-facing admin, deployment, and development skills are available from the repository's `.agent/skills` directory so AI agents share the same operating instructions. `.agent/` is the only repository directory for agent support files; there are no `.agents/`, `.codex/`, or `.claude/` directories or `CLAUDE.md` compatibility link. Root `AGENTS.md` defines working instructions.
- `./bin/nocheh` is the single owner-facing command for installation, admin inspection, deployment, archive, security, and security profile operations. Its command flags, output formats, privacy defaults, and data contracts are stable.
- Repository tooling lives in `tools/cli`, `tools/operations`, `tools/runtime`, `tools/acceptance`, `tools/development`, and `tools/build`. The dashboard source lives in `dashboard`; TypeScript services live in `src`; Nocheh's Hermes plugin and Honcho service code live in `services/hermes` and `services/honcho`. The Hermes plugin retains its `plugin.yaml` identity and `plugins/nocheh` profile links. Agent skills live in `.agent/skills/nocheh-admin-cli` and `.agent/skills/nocheh-deploy`.
- Repository checkouts and live source mounts use those canonical paths, with no legacy `integrations/`, `scripts/`, `web/`, or `admin/` directories.
- Repository files and directories have a defined product, tooling, test, acceptance, or documentation role. The tracked tree contains no empty files or directories.
- Git tracks source code, build and deployment configuration, documentation, and explicitly synthetic test fixtures. Runtime state, generated output, live acceptance reports, source content, operational identifiers, credentials, and installation metadata remain in local ignored state outside repository commits and Git history. Tracked acceptance material contains reusable procedures and non-identifying status summaries.
- Database size and other operational storage do not grow uncontrolled in any component. Owned original source data is retained without a bound by design. By owner decision ("keep data for ever"), workflow history and Hermes delivery logs are also kept forever unless the owner sets a retention period.
- The setup has one clean structure: root `docker-compose.yml` defines the three-store installation directly, with no separate storage-layout overlay or selectable legacy runtime. Compose creates owned volumes for a fresh installation.
- Local development uses the root `docker-compose.dev.yml` override with the operating Compose file; isolated test configuration lives under `deploy/acceptance`. The development launcher verifies operating state and service ownership before starting.
- Local development runs the full operating Compose project of the checkout's workspace (`nocheh` for `personal`), including Honcho, in source-watched mode on that workspace's localhost ports, using the configured Telegram bot, local application data, and the installation's provider keys and credentials. The existing `nocheh-app` service watches mounted source code, compiles changes, and reloads running services live without manually rerunning the app or rebuilding Docker images for ordinary source edits; development adds no builder service. Each workspace runs one Compose stack at a time, and each Telegram bot has one poller; other workspaces may run beside development. Switching between development and unattended operation preserves the same source data, memory, and bot identity.
- Deployment service names identify their tool and purpose. `nocheh-app` combines the API, source capture, outbox publication, and ordinary Inngest handlers; `nocheh-security` combines the broker and guard outside agent execution. The single managed Hermes core service is named `hermes`; its isolated-agent sandbox launcher is named `hermes-agent-sb`; and Nocheh's PostgreSQL service is named `nocheh-db`. Hermes serves its built native dashboard through its managed web server. The owner dashboard and executor run as separate Docker services, independently of the application and Inngest. The executor service is named `nocheh-executor`. Stores, credential-bearing gateways, and isolated agent launch authority retain separate boundaries.
- The supported Node runtime is 26.x. Ordinary workflow execution has concurrency four, executor workflows two, and separate API/capture and workflow PostgreSQL pools capped at eight connections each. Inngest outages cannot prevent capture, API startup, or management operations while Docker is available.
- Nocheh uses three databases on its PostgreSQL service, with separate credentials and explicit repository interfaces: `nocheh_archive` for original evidence, `nocheh_derived` for guarded versions and generated data, and `nocheh_control` for configuration, audience policy, projects, sharing permissions, approvals, jobs, retries, authorization epochs, and execution receipts. Hermes, Honcho, and Inngest retain their separate native stores. Provider monitoring may retain its own operational SQLite state.
- The PostgreSQL service provisions the archive, derivative, control, and workflow databases before it reports healthy. Nocheh has no standalone `nocheh-store-bootstrap` service. The running application and security services use restricted store roles, never the installation administrator credential.
- Product source data is portable across runtime and memory implementations. A replacement runtime satisfies the same capability, capture, audience, and enforcement contracts.

<area name="Archive and provenance">

- The archive database contains only original observations, messages and edits, source identities, observed relationships, original file manifests, hashes, and capture provenance. Originals keep the chat and topic ids their app gave them and are never rewritten or indexed by chat; a read reaches a chat's originals through every app id the chat has had, current or old. Original file bytes live in the owned immutable file store. All guarded versions, transcripts, extractions, generated artifacts, runtime context, and learned interpretations live outside the archive in `nocheh_derived`.
- Files are important: their text is read at capture and import and goes through the secret check, since a file may include credentials. Nocheh calls a ready reader (Hermes's document reader for Word, Excel, PowerPoint, old Office, OpenDocument, RTF, EPUB and PDF) from its own preparation step instead of building its own.
- Photos and image files are read once when they are saved, live or imported, by Hermes's own vision tool with the Images model of Settings › Models (the main model unless the owner picks another). The reading is the image's text and a short description, from an instruction the owner can edit in Settings › Assistant; it goes through the secret check, since a screenshot may show a credential, and the original image is kept. A reply waits for it; a busy provider is tried again, and an image that cannot be read records why. Stickers, animations and video keep their original only. Each reading's tokens and cost show on the Usage page, and an import shows how many images it will read and what that costs before it starts. Telegram sends a photo as several sizes of one picture; only the largest is downloaded, read and checked, and the saved message still lists the other sizes.
- Original audio, video, and files are the source; transcripts and extractions are replaceable, versioned derivatives. Every derivative retains stable typed source references, source revision, input hash, producer/version, and configuration fingerprint. A model output never replaces an original.
- Observed incoming messages and successfully delivered assistant messages are source evidence of what was said. Drafts, prompts, internal contexts, generated shares, schedule definitions/fires, and execution attempts are not source observations and remain outside the archive.
- Every confirmed delivered assistant message appears as an original source record with its observed text in the Messages page's Assistant replies filter, including replies recovered from retained delivery receipts. Conversation filter counts reflect source records shown in Messages rather than operational records.
- Incoming Telegram events enter a durable spool before acknowledgment and commit idempotently before downstream assistant processing. An update that the runtime's Telegram library cannot parse never stops polling: its original is captured whole, polling advances past it, and the count is visible in polling health. Duplicate updates, database outages, restarts, partial downloads, and retries preserve observations and recoverable progress.
- The owner can retire or restore any captured Telegram message, including text, voice, media, edited messages, and confirmed assistant replies, from Messages. A retirement is an owner decision in control storage keyed to the stable message identity, so every observed revision shares it. The action uses a revision check and idempotent operation ID, and its history remains inspectable. Originals, files, transcripts, and delivery evidence stay immutable and available to the owner. Messages labels retirement separately from reply and delivery status; retirement is never labeled as an observed Telegram deletion.
- Message management in Messages makes retirement easy to complete and understand: a reversible retirement takes one explicit action, its saved active or retired state remains visible beside that action, failure appears in place, and restoration is clearly offered as Undo. The interface explains that retirement does not delete the original or recall a Telegram reply already sent. When the owner retires a message, Messages also offers the delivered assistant replies that directly answered it or repeat a substantial verbatim excerpt of it, and the owner can retire the selected replies in the same action. Offered replies remain available unless the owner selects them.
- A retired message and reactions on it are excluded from future agent retrieval and learning. Dependent contexts and inferred conclusions are invalidated before reuse and rebuilt only from remaining permitted evidence. Retirement stops a pending reply and requests cancellation of a running turn before delivery begins. A confirmed sent reply remains confirmed; an uncertain send remains uncertain and is never automatically repeated or labeled cancelled without a cancellation receipt. Restoring a message permits future use without rewriting history. A second message never implicitly retires the first.
- On retirement, Hermes' own stored conversation history replaces a retired message with a placeholder that says it was retired and gives its message ID (its archive source ID); a retired assistant reply is replaced the same way. A retired message that a group turn carried as a recent message, or that any turn quoted as the message it replied to, is replaced the same way inside that turn, and the turn's tool calls and results and the notes written from them are withheld and removed with it; the turn's own message and its delivered answer stay; a tool result that held a retired message's text counts the same way for the rest of its turn. A later turn in the same conversation whose note copied a retired message's text is withheld the same way, with that note. A stored recall or opened fact that rests on a retired message is withheld the same way. Until a profile's next turn brings it current, owner recall skips the history rows and notes that turn will withhold. Restoring a message does not restore it in Hermes' history.
- When asked which message came immediately before the current one, Nocheh does not treat the current question or the latest accessible history item as proof of that order. If the order cannot be verified across messages it may not access, it states that uncertainty without revealing retired content.
- When asked what a retired message contained or was about, Nocheh does not treat the current question or another accessible message as the retired source. If the retired content is unavailable to the agent, it states that it cannot determine the content.
- Capture, attachment retrieval, assistant work, and approved actions have independent progress; slow inference does not block source capture. Unsupported or malformed input is retained with a visible processing outcome.
- Browser text and attachments are captured before command interpretation or inference. Scheduled definitions and fires retain stable operational identities in control storage. Outbound results, execution attempts, and delivery receipts remain separate evidence; confirmed delivered messages can reference that evidence.
- The agent can read a chat in order, oldest first, page by page or between two dates, with each page saying how far it has read; only the owner may name another chat. In chats that were learned, it can also find messages by meaning rather than exact words. Both give back only what the reader may read, after the secret check.
- When a request needs more than a reply can do, such as reading a long chat, the agent checks its size, then offers a background job with an estimate of its cost and time and Approve and Reject buttons. The person who asked approves it, or the owner when a member's job is over the owner's cost limit or its cost is unknown. An approved job runs step after step in its own session, keeps its to-do list, stops at its cost or time limit with a report of what it found, and sends its report to the chat where it was asked, except a job on one of the owner's machines, whose report goes to the owner's private chat (see Machines). A job can be stopped at any time; a stopped job sends no report. At most two jobs run at once. A member starts small jobs in a group with no daily limit while they may talk to Nocheh there and their small jobs permission is on (see Members); a member's job stops when that no longer holds. A job the owner asks for in their private chat can also run commands, edit files and run Python in a sealed box, unless the owner turns that off in Settings › Assistant, and its card says so before it is approved. The box has no internet and no keys, so its commands run without asking. Nocheh copies into it only the job's chat messages that passed the secret check; the job can also keep its own files there, such as what its other tools returned, and they are lost when the job ends. A job the owner asks for can instead work on one of the owner's machines (see Machines). A member's job is capped at the owner's cost limit or 1.5 times its estimate, whichever is higher, counted to the cent. When the jobs members approved themselves pass the notice mark in a UTC day ($20 by default), the owner gets one private Telegram notice with a Pause button; past the pause mark ($100 by default), member jobs pause by themselves until 00:00 UTC and the owner gets a notice with a Resume button. A pause holds approved member jobs, which say so on their cards and start when it ends; nothing is refused, and the owner's own jobs and member jobs the owner approved never wait. Both marks are in Settings › Assistant › Background jobs; the owner pauses or resumes from the notice or from System › Background work.
- A job's card shows its title, instruction and plan as typed, with each character a reader would not see written out where it stands; Persian half-spaces and emoji show as typed. A job whose text could read in another order than it runs is refused. A job's card in another chat than the one where it was asked says where it was asked.
- Nocheh reaches GitHub through its own GitHub App, not a personal token. The owner connects it from the dashboard and chooses on GitHub which repositories it may read.
- Search, source reads, artifact downloads, graphs, export, and replay preserve identities and enforce audience access. Queries are bounded and paginated. Archive search and the default archive graph show original evidence; source details link to derivatives. Knowledge retrieval can combine authorized sources and memory with clear labels.
- Every search hit and every opened message the agent reads names who wrote it, where and when, in a short tag Nocheh's code builds from the archive, never the model, beside everything the result showed before, and says whose words they are (the owner's own typing, another person's, a forward, a file, several kinds, Nocheh's own, or shared by the owner). The owner reads times in the Settings › Tasks time zone, with the zone named, and a name the owner gave someone in People beside the name Telegram showed; everyone else reads UTC and only names Telegram showed. In a group the owner's own messages are named by the owner's Telegram name, and a person who calls themselves "the owner" is still another person. A tag never tells a reader about a chat, a person's saved name, a topic name or a time zone that reader may not read. Opening a message also shows what it replies to and the replies to it, each only where the reader may read it; a message in a forum topic is no reply to the topic's opening. Owner recall's hits from stored chat history show their own text and when they were said, never the rows around them.
- Every fact of long-term memory the agent reads, in a turn's memory or from recall, sits under a source line Nocheh's code builds from the messages it was learned from, with the time of its message, in the same words and limits as a search hit's tag. The person the fact is about comes first, so a fact about Bob that rests on the owner's question names Bob; it reads as the owner's own words only when every message it rests on is the owner's own typing, and a fact known only with the messages it was learned with says it is not exact. Any fact opens by its memory id and number, with the messages it came from, only for readers of that memory; one whose message was retired, or that memory no longer holds, does not open. Recall lists the facts it read with their first sources instead of a bare list of messages, except where facts can't be listed. A turn's memory stays within its earlier size limit; when its facts can't be named, it reads as before and the problem is counted.
- A turn whose message replies to another message reads that message before its own text, named in the same words and limits as a search hit's tag and saying whose words it is (Nocheh's own reply reads as Nocheh's), with at most 200 characters of the text its reader's copy holds, which no message text can imitate. Each recent group message a turn reads that replies to another names that message the same way, without its text. Only a message the reader may read is named; a retired one, one in a chat the reader can't reach, or a forum topic's opening, which every message in the topic replies to, is not. Retiring the replied-to message withholds the quote and that turn's tool work and notes, as for a recent message.
- The owner's dashboard shows where messages and facts came from, and only to the owner. A message's detail in Messages shows its thread (what it replies to, its forum topic with the topic's first message, where a forward came from, and the replies to it) and the facts long-term memory learned from it, each marked as naming its exact source or as learned with other messages; a message in a forum topic shows its topic, never the topic's first message as what it replies to, and that first message lists no replies. Memory › Long-term lists the facts long-term memory learned, newest first, filtered by chat or by person, each with when it was learned and links to the messages it came from, under a line counting how many name their exact messages, how many were learned with other messages and how many name none; re-running or replacing memory still asks first. Each note in Memory › Assistant notes shows its day and links to the messages it was written from. Someone else's private chat stays out of what the owner sees by default: another chat's thread never shows or links its messages. Every linked message, on these pages and on Facts, People, Projects and Inbox review, carries a short label in the owner's own words and when it was sent. A retired message is never linked: it reads only as hidden from the assistant. A label that cannot be read shows no link and is counted on System › Health; looking changes nothing and nothing is learned again.
- Messages browse pages show the newest received source records first, with a stable order for records received at the same time.
- Messages leaves other people's private chats with Nocheh, members' and strangers', out of its default list, so they never show when the owner shares their screen, and keeps them under their own “Members’ chats” filter.
- The owner dashboard presents archive records in a searchable, paginated, responsive table. Its default browse and search results contain all source records only, excluding wire captures, outbound intents/results, generated drafts, and other operational records. Visible filters let the owner narrow those results by message direction, conversation scope, and reply-processing state; source-only filtering is never an invisible fixed choice. The table identifies message type and conversation alongside the message, uses a status column for incoming reply processing and confirmed outgoing delivery, and shows the delivered assistant message beneath the incoming message when a durable causal link is available; that linked message opens its own immutable source record. Incoming messages show reply-processing state separately from capture and guarded-copy readiness. A pre-delivery failure is labeled as retry scheduled, while a genuinely uncertain Telegram delivery is labeled as delivery uncertain and explicitly not auto-retried; neither state is described as an approval. A reply that Telegram definitively rejected is labeled as rejected by Telegram, and a voice note without a transcription provider is labeled as archived without transcription; neither is described as a reply that was not needed. Selecting a row opens a concise message detail view in a side drawer over the table, rather than below the page, led by the immutable original and the revision-checked editable agent copy. Active transcripts are visible in the ordinary message detail and labeled as generated; other generated items, provenance, raw fields, source identity, and export controls remain available under clearly labeled advanced details instead of dominating the ordinary view; immutable original evidence remains visibly read-only and is never edited as a raw database row.
- While the Messages page is open, it receives a live refresh stream and shows new and changed source records, conversation counts, reply state, and selected-message details without a manual reload. Refreshes preserve the active search, filters, selection, and pagination. The view reconnects after interruption and identifies when its live connection is unavailable.
- Messages shows a conversation reply and each associated external action as separate outcomes. When an incoming message has a proposed Telegram action, its row visibly says approval is pending and links to that exact review, including when the conversation reply was already sent. Approval and action execution do not count as confirmed Telegram delivery. The owner can filter incoming messages with pending action approval.
- Message rows and original-message details identify voice and other non-text content by its original content type, including when the message has no text. When text and non-text content coexist, both remain visible. The owner can see attachment readiness, download original files, and explicitly preview supported audio, video, and images without automatically loading them. Missing text is never presented as missing message content.
- Reaction rows in Messages show more detail of reactions: observed additions, changes, removals, and anonymous count updates. Each row shows the reaction emoji or known type, the actor when Telegram supplies one, and the target message ID. Unknown reaction types and incomplete observations remain labeled as unknown or updated without assigning meaning or implying current state.
- A voice message plays from its message detail with one deliberate play action when playback is allowed by the browser. The active transcript is readable alongside the original audio and visibly distinguished as generated text. In Messages browse and search rows, a preview of the first active transcript appears beneath the original message content and before any linked assistant reply, labeled as generated text. When no active transcript exists, the detail says so explicitly and the row retains its original content type without a transcript preview.

<area name="Versioned derivatives and reprocessing">

- The owner can list derivative versions, inspect provenance, reprocess selected sources from original bytes, and activate a prepared version through the dashboard, API, and CLI. Jobs are idempotent and edits use revision checks.
- Reprocessing preserves immutable output versions, original bytes, and owner-edited guarded versions. Guard preparation succeeds before activation. An old owner edit is never silently applied to different generated text.
- Changing the active derivative invalidates dependent contexts and refreshes affected learning. Completed derivative results are durable before workflow completion receipts.

<area name="Imports and portability">

- The database design supports long-term data import across platforms, including future Slack and Discord adapters, and its chat records cover Slack for the future: a workspace, its channels, and its people and their standing; a Slack thread, like a Telegram reply chain, stays at message level and is never a chat of its own. Every chat has an opaque Nocheh id of its own that never changes and holds no bot, so replacing an app's bot keeps every chat; every id an app has given the chat, current or old, maps to it. Adding a platform preserves existing source data, identities, provenance, audience boundaries, and the ids existing chats already have.
- Manual import accepts Telegram Desktop single-chat and multi-chat JSON exports with supplied media, including ZIP input. Preview shows scopes, message counts, dates, and missing files; missing media does not make supplied text unusable.
- Imported history defaults to owner-private scope. Mapping it to an existing group requires explicit owner selection; Desktop identities are not guessed to be Bot API identities.
- Importing group chat history from exported Telegram data is fully compatible and prevents duplicates and similar issues. Identities that Telegram proves are shared: a Desktop sender is the same person or chat the bot sees live, and a supergroup or channel export mapped to that same live chat contains the same messages. A message already captured live keeps its imported copy as evidence, counts as a duplicate, and is neither learned nor retrieved twice; a newer export of a message replaces the older one in memory.
- Import jobs persist progress, duplicates, revisions, errors, cancellation, and resumable identities. Uploads and extraction are bounded and reject escaping paths and symlinks. The supplied export bytes retain import provenance.
- Historical import and replay send no old conversation replies. Importing makes sources searchable; learning requires explicit opt-in at import confirmation, retained across retries.
- Nothing runs at import except storing, preparing (reading files) and the secret check. The secret check runs once at import and is saved, checking many messages of the import in one call. A Telegram Desktop export's messages file (result.json) can be up to 128 MB, and the messages file is not re-sent with every batch.
- The Import page shows each step's progress: saving, reading files, secret check. The import is marked ready when those are done, and the owner gets a Telegram message. Until then, a question about that chat says it's still importing and how far along it is. The page shows the learning cost estimate before the owner presses Start; an estimate is acceptable.
- Source-only exports preserve original observations, files, identities, and capture provenance. Complete portable exports also preserve generated records and guarded history in separately labeled domains. Reimport routes records to their proper stores. Accepting saved guarded copies requires an explicit trusted restore; ordinary imports prepare their own projections and divergent histories are conflicts.
- Portable export also includes registered native profiles' notes, scope markers, and SQLite session snapshots including committed WAL state. Runtime-generated material is labeled separately. Per-file hashes and a completion manifest support verification; operational credentials and configuration are excluded.
- Portable export does not activate an installation or imply one common recovery snapshot. A quiesced backup supplies a common recovery point.
- Portable export includes the owner's tasks (with comments, reminders and who set each and where, people, links, files and history), schedules, sharing rules, project chats, the chats Nocheh knows with every app id they have had, hidden sources, learning choices, topic names the owner gave, edited built-in texts and settings. Import never makes them act by themselves: imported chats arrive not served, sharing rules arrive switched off, missed reminders do not fire late, and scheduled jobs stay staged until the owner adopts them. The names people gave themselves in a chat app are not exported with who set a reminder or wrote a task.
- Portable import retains access settings, requests, grants, and decisions as inspectable history. It does not create active grants or replace the destination's access settings, even when installation generation and authorization revisions match.
- Complete portable export and coordinated backup preserve knowledge proposals, organization delegation history, decisions, and application and undo receipts. Portable import retains saved authority as inactive history. Import and inactive restore cannot enable organization permissions or reactivate queued organization work through restored control records.

<area name="Platform-independent source model">

- Source identity separates platform, source namespace, object kind, and opaque external string ID from connector installations, import jobs, and local audiences. A chat's app id is a label of the chat, not its identity: Nocheh names each chat by its own id. Separate observations may refer to the same source object and revision without losing their distinct originals or provenance. Unproven identity mappings remain separate.
- Common source relationships include authors, containers, threads, replies, reactions, and attachments. Reaction observations preserve the target message, reaction, actor when supplied, source timing, and observed changes, including activity on old messages. Source objects also represent non-message data. Unknown platform fields are preserved; partial, complete, unknown, and observed-deletion states remain distinguishable without inferring missing history or revision order.
- Relational identities and relationships support common queries; versioned metadata retains platform-specific extensions. Supplied original bytes remain separate from normalized projections. Projection metadata does not bypass guarding or audience access.
- Adapters and source projections carry explicit versions. Database migrations preserve existing source references, original evidence, guarded revisions, learning consent, and export/reimport behavior. Source hierarchy and relationship targets do not grant audience access.

<area name="Guarded projections">

- Guarding has two modes: `on` and `off`, with `on` the default. Durable guarded projections are prepared at ingestion for source revisions, including imported and derived text, and reused without repeated detection of the same prepared content. Guard inputs, outputs, revision history, and owner edits live in `nocheh_derived`; guard policy and authorization epochs live in `nocheh_control`. Owner edits are durable data, never disposable caches.
- A trusted model detects literal secret substrings; local code validates literal membership and spans, merges overlaps, and masks them. All other text remains exactly unchanged. Detection quality is measured; it is not a guarantee that every possible secret is found. A secret found by one check hides the same text in another chat only when that check, or a check of that text alone, found it. Field names, and a model request's roles, types, names, model and tool ids, are never hidden because of what the model found, only by the fixed secret formats.
- Ordinary phrases and synthetic test markers in voice transcripts remain readable when they are not used as credentials. A credential label or unmistakable credential value remains guarded.
- The owner can inspect originals, file bytes, preparation status, guarded copies, and revision history. Only guarded projections are editable. Saves use revision checks; restoration creates a new revision. Saved owner edits are authoritative and cannot be re-masked or overwritten by background preparation.
- `on` selects only current guarded data for agents, tools, memory, and embeddings, including trusted reasoning routes. `off` selects originals with the same audience and effect checks. Guarding is neither archive encryption nor a switch that disables authorization.
- Preparation persists completed work and retries incomplete work. Unknown, unavailable, stale, or unbound guarded context fails closed without an original-data fallback.
- Every physical model attempt validates current content revisions, audience, and destination, including complete history, native memory, retrieved sources, tool results, auxiliary calls, redirects, retries, and provider changes. Unsupported transports, opaque server-side history, and provider-hosted tools that bypass this boundary are rejected.
- Trusted detection and media preparation receive the original inputs necessary for their task. Raw media reaches only explicitly trusted perception or transcription destinations; resulting text is stored and prepared under the same policy as typed text. Model names alone confer no trust.
- Owner edits and representation changes retire affected contexts, credentials, caches, and Honcho sessions before reuse. Revocation precedes availability of changed guards or access policies; interrupted changes stay unavailable until reconciliation completes. Rebuilding uses current authorized sources; original and guarded Honcho memory does not mix. Retiring local data cannot retract data already delivered externally.

<area name="Memory and audience access">

- The owner's private side (private chat, notes, Notion, machines, personal tasks) never reaches a group or a member except through a card in the owner's private chat, or the owner's own confirm in the dashboard or mini app, that names who will see it. Only groups and their topics share, are shared with, or join a project; every other chat, the owner's private chat and its topics included, counts as private, and anything Nocheh cannot place counts as private too. Nocheh places a chat from its own record of it, never from how an app writes the chat's id: a chat it has no record of is not served, reads nothing, and never joins a project, a sharing rule or a private answer's groups.
- The owner's private assistant can recall across all registered native memories and archived sources, except members' and strangers' private chats and the notes of a member's private chat. Groups and topics use versioned `isolated`, `approved` (default), or explicitly selected `filtered` sharing. Topics inherit group preferences and keep distinct conversation history. By default, all topics of a group share one memory: a turn in a group's General chat or in any of its topics recalls what was said in all of them. The owner can instead keep each topic's memory separate with “Topic memory” in Chats › Sharing or Settings › Telegram; “Whole group” is the default. Each note the owner's recall finds says where it came from: the owner's private chat, a group or topic by name, or a private answer and the group it was asked in.
- Telegram General-topic handling supports ordinary messages without topic markers in the group's base conversation scope, which shares the group's memory with its named topics unless the owner keeps topic memory separate. A topic is a chat of its own under its group, found by its group and its topic key, and captured originals keep the app's ids and are read through the group's and topic's chats. Existing captured General messages can resume from their original envelopes without rewriting archive evidence. Incomplete or malformed topic markers remain unresolved and do not broaden access.
- Audience access is enforced in storage, tools, source reads, file access, notes, sessions, graphs, and delivery. Policy changes invalidate stale capabilities and contexts; audience authorization is rechecked before delivery. A memory engine's model may run only the tools its request offered, so a group's memory read never reaches another conversation.
- Each physical Telegram send, including response chunks and native retry or formatting fallbacks, preserves the authorized chat and topic and rechecks current authority and cancellation. An unavailable topic never permits delivery in General or another topic. Each send goes to the chat's and topic's current Telegram ids, so a send follows a group Telegram gave a new id, and nothing is sent to a chat Nocheh has no record of. A turn is bound to where its chat and topic are in the app, and a turn whose binding does not match the message it answers is refused. A partially delivered response is not automatically repeated or described as fully cancelled.
- Approved shares expose exact owner-approved content revisions. They do not grant access to private originals or private provenance. Filtered sharing exposes only derived material reviewed for the target audience from sources the owner selected; failures withhold wider knowledge. Semantic privacy filtering is fallible and separate from provider guarding. The filter's model sees only the words that were searched for, at most the 12 longest, sorted, never the asker's question. The Filter automatically choice says that people in those chats can talk the filter into passing more, and points to "I approve each text" for private talk.
- Live conversations can drive native memory review. Imported-content learning needs explicit approval during import; preparation or attachment does not grant that approval. Imported history is learned by long-term memory only: Honcho reads and summarizes it, with no native memory review and no learning question about each message. Background review has no external-action tools and keeps source facts separate from inferences.
- Every native note names where it came from, in a label Nocheh's code builds from its own record of who wrote the note and what that run read, never from the note's text or from a model. A note reads as the owner's own only when a notes review drew it from nothing but the owner's own messages, read no rule learned from anyone else's words, and it cites them; a note written during a turn never does. Whose words a rule rests on is what Nocheh recorded it was learned from, never what a model cited. A pin carries the words of the message it pinned, and the owner's quote or pin of a message Nocheh learned as its own counts as Nocheh's, not someone else's. The model reads the label beside the unchanged note, as information about it, and someone else's words in a note are never the owner's words or instructions. The owner reads the label, in editable words, under each note in Memory › Assistant notes, and each note found by recall carries its own label, its day and the first messages it was written from. A note written in a turn whose message replied to anyone's message but the owner's own typing says it was written after reading that message, Nocheh's own messages included; later in the conversation only a note that copies from the replied-to text does. A review's label names the day of the message it is named by, and a turn's note the day it was written, in the reader's time zone (the owner's chat in the Settings › Tasks zone, everyone else in UTC). In the turn whose memory shows a note, the agent can open the messages it was written from, read-checked like any source, and only in that turn. A note with no record says its source was not recorded.
- Nocheh does not limit incoming data in a group from anyone: it sees and reads everything in a group it serves, the data and other content of people who are not members too (their messages, files, photos and voice notes, read whole, with no daily budget), and only does not let them interact with the agent.
- A message from someone who is not allowed where they wrote stays out of the owner's native notes, and only there: group replies, the group's long-term memory, interpretations and search still use it. A pin of their message is reviewed without it. Making that person a member later, or switching them on there, does not add their earlier messages to the notes. Memory › Assistant notes says how many messages were kept out, and System › Background work says why on each one's memory step.
- Nothing in a private chat other than the owner's, and no answer to the owner's question about a member, is ever learned, made learnable by the owner, granted, requested or suggested.
- Nocheh's own cards, card updates, refusals, notices and reminders are kept, searchable and context for a reply to them, but are not learned unless the owner turns learning on for one. Its replies, follow-ups, private answers, job reports, scheduled results and approved posts are learned, each labelled as what it is.
- Memories and retrieved content are evidence, never security policy or action approval. Conversation conventions guide interpretation within those boundaries. The security boundary preserves complete authorized native memory, source references, history, model choice, reasoning settings, and configured context limits without introducing lossy summaries or extra context-work approvals.

<area name="Conversation state and conventions">

- The agent automatically learns contextual meanings and traces the state of tasks, commitments, and other subjects from permitted message relationships, reactions, edits, and stated conventions in background learning, even when it does not reply. New activity on an old message can update the agent's understanding. Learning itself sends no acknowledgment or external action.
- A "check" emoji reaction on an old message can mean it is done; this is a contextual interpretation, not a fixed meaning for that emoji. The agent learns how people use reactions and relationships from the conversation and its conventions, preserving uncertainty when the meaning is unclear.
- Explicit interpretation rules can be supplied in the infrastructure system prompt, in each group or project's contribution rules, or stated by any participant in the group. Local rules apply locally; project-wide rules require an unambiguous project reference. Explicit applicable conventions take precedence over inferred defaults. Conflicting explicit conventions stay visible until evidence or an owner correction resolves them.
- Inferred state and conventions live in `nocheh_derived`, retain source activity, applicable scope/rules, uncertainty, producer details, conflicts, and revision history, and remain distinguishable from observed facts. Later activity, corrections, or rule changes can revise them. Original observations remain in the archive and their guarded representations remain in derived storage.
- The owner can inspect what Nocheh learned, filter by scope, follow evidence, inspect history and conflicts, and correct or retire interpretations in the dashboard, API, and CLI. Owner corrections override the affected interpretation and invalidate or rebuild dependent memory contexts before reuse.
- Learned interpretation cards display their details as badges, visibly identify revised entries and the active revision, and align action buttons across cards in each row. The dashboard can filter revised entries. An interpretation's detail view shows the active and original wording together after a revision, keeps the complete revision history accessible, and confirms a saved correction without obscuring the original wording.
- Contextual interpretation uses guarded Honcho reasoning with authorized evidence and applicable conventions. By owner decision ("dont apply limit use memory fully and use all features"), learning uses Honcho memory and its features fully, apart from peer cards, which stay off as described under Honcho and native memory: Honcho's question limit is set to its 200,000-character maximum, and a learning question can use about half of Honcho's reasoning input budget (92,160 UTF-8 bytes), leaving the rest for the memory Honcho gathers, so that every model request fits the size the secret check accepts. Nocheh shortens a question only past that size.
- A bounded provenance reader follows conclusion ancestry to ingested source references. Memory evidence shows the exact messages a memory came from whenever Honcho records them, lists them first, and says when any conclusion's sources are not an exact citation; the owner provenance view marks each conclusion as exactly cited or not.
- Reply/reaction context resolves independently of graph pagination. Duplicate, delayed, removed, anonymous aggregate, and unresolved observations remain distinguishable; missing context is not invented and unknown topic membership does not broaden access.
- The Telegram adapter explicitly subscribes to individual and anonymous count reaction updates when Telegram delivers them. Every update remains original evidence. Current individual reaction state is maintained per target and actor, with anonymous counts separate. Changed or removed reactions make superseded observations and inferences unavailable even when no replacement conclusion is produced. Edits and reactions on old messages update learning silently and do not trigger a reply to that old conversation.
- Interpreting a reaction or group convention does not grant action approval or change administrative, provider, privacy, or guard policy. State inference follows the same audience and learning-consent boundaries as other memory.

A change that would give one rule more than 100 sources, or one group more than 10 enabled filtered rules, is refused and leaves every revision unchanged. Previews and released texts of a rule's earlier revisions are no longer used. An approved text is released for one rule and reaches only that rule's destination.

<area name="Honcho and native memory">

- Honcho is the primary long-term memory, with reasoning through the memory part's provider and dedicated capped embeddings. Hermes keeps small native `MEMORY.md` and `USER.md` notes alongside Honcho and retains its native sessions.
- For the MVP, Honcho is used as long-term memory under Hermes. Honcho can also be used directly in the future without Hermes, through Nocheh's memory interface.
- Long-term memory sits behind one memory socket inside Nocheh: feeding writes in, start-of-turn context, recall and search, and corrections and deletions. Nocheh keeps the receipts, sessions, sharing rules and deletion bookkeeping; the engine only stores, learns and answers. Honcho is the only engine today; another engine, such as mem0, can replace it without changing how a brain reaches memory, which is always through Nocheh. A different engine starts a new, empty memory space, and the owner chooses whether it learns the archive again. The dashboard shows which engine is plugged in.
- Nocheh's Honcho usage definition follows what Honcho's documentation describes, and each user, project, etc. is defined as an entity. A non-standard Honcho usage pattern with high cost is not used.
- Fresh local installations enable and prepare the Honcho service by default, and Honcho memory is turned on for ordinary turns by default once the service is enabled. No live acceptance test is required before it turns on. The owner can turn it off, and the owner's choice stands across restarts; an explicit installation setting can disable the service. Turning it on does not ingest earlier history unless the owner selects that option.
- Honcho production support and read-only inspection are part of the installed memory integration. No separate Hermes-versus-Honcho comparison runtime or experiment workflow is shipped.
- People and projects are the entity types used for connected memory. Exact platform identities are reused automatically. Different people with the same name remain separate; ambiguous name-based or cross-platform matches remain suggestions until the owner confirms them. Registered projects are reused. Evidence-backed discovery may create a project under explicit bounded organization permission; newly discovered projects outside that permission and uncertain project identities require owner confirmation. This exception grants no authority to link people or merge identities.
- Suggestions that are all the same person or project are merged into one waiting item, automatically or by the owner's manual merge. The owner sees every name on that item before confirming it, can take a wrongly merged name back out, and one answer covers every name.
- An unambiguous reference to a confirmed project attributes that statement to the referenced project instead of the conversation's default project. It does not reassign the conversation or change access permissions.
- Contextual mentions, participation, responsibility, dependencies, and explicit associations are distinct relationship types. Mentioning one project in another project's conversation establishes only a contextual connection unless stronger evidence establishes another relationship.
- Every entity claim and relationship retains source references, the actual speaker, direct/reported/inferred attribution, uncertainty, revision history, and applicable audience. A reported claim never becomes a direct statement by its subject, and a generated interpretation never becomes independent corroborating evidence. Nocheh's code, not the model, decides that a claim is direct: one that rests on a forwarded message, a file's text or someone else's message is recorded as reported or inferred.
- Canonical identities, confirmed bindings, and review decisions live in control storage. Extracted claims and relationships live in derived storage. Original evidence remains in the archive. Owner corrections override automatic interpretations: chosen person names, confirmed identity links, corrected fact wording, and retired facts survive later platform or model updates. New messages use the confirmed identity binding. Identity links can be undone, and dependent memory is invalidated and rebuilt.
- An installation uses one Honcho workspace. Each person and confirmed project has a stable, versioned Honcho peer mapping derived from its Nocheh identity, and the assistant is its own peer whose messages Honcho does not observe. A project is both a Honcho peer and a session. Each chat, group, topic, import, and project uses its own Honcho sessions, and each session belongs to exactly one audience. A chat's audience is named by its Nocheh chat id, so a chat keeps its sessions when an app gives it a new id. Conversational messages use their actual speaker and persistent conversation sessions. Project and mentioned-person observations use separate typed entity-evidence sessions that identify the subject, speaker, source, and attribution without making the subject appear to have spoken. One more peer that is not a person, the owner's forwards and files, writes what other people wrote that reaches the owner. Someone else's message the owner forwards in the private chat goes to the owner's own forwards session, and a short fixed note in the chat says only that something was forwarded and from what kind of sender; the text of a file or audio the owner sends stays in its chat session but is written by that peer; in a group, the owner's forwards and files go to that peer in the group's own session. Each record names its source in fixed words. A message already learned keeps the form it was learned in until the owner replaces long-term memory.
- Every assistant turn receives bounded, current, authorized Honcho context automatically. Protected context is rebuilt when Honcho finishes new memory work, and its freshness is checked when a message arrives; it is not refreshed on a timer. Deeper Honcho recall retrieves relevant details missing from that context. Ordinary turns do not require an unconditional Honcho reasoning call. Cached context never crosses audiences or survives revocation, representation changes, or a failed freshness check as usable memory.
- A reply reads Honcho's context for its own conversation session, targeted at the speaker. The owner's private conversation can read the whole workspace. A group or topic turn reads only its own chat (all of its project's groups while the project shares its group chats), including the sessions of every topic Nocheh has recorded under its group unless the owner keeps topic memory separate, plus facts the owner approved for sharing, never a person's unrestricted Honcho representation. A private answer reads only the groups frozen when its Answer privately button was tapped: the asking group and the other groups of its project that the asker is in (for the owner, all of the project's groups), with every topic recorded under those groups, by plain search in long-term memory only. It gets what the owner's sharing rules and grants let into the asking group, and never reads the owner's private chat. A member's private chat reads the sessions of the groups it may read, by plain search only, and gets nothing shared or granted. Owner-private evidence is never written into a session shared with a group or topic. Honcho peer cards, which summarize a person across every session, are turned off, and no Honcho context Nocheh reads includes one. The owner's turn reads what is known about the owner and what came through the owner's forwards and files as two separate blocks, each saying what it is; recall from the private chat looks in both, and when the forwards and files can't be read it keeps the rest and says so.
- Each Answer privately is recorded: who asked (their account), where, which groups the answer may read (by their Nocheh chat ids); the groups are fixed at the tap, so a later change can't widen an old answer. A private answer only reads: it never writes, posts or acts, it reads text, transcripts and extracted file text but no group's original file, and what it may read always comes from its record, never from the turn. A later change in the project only narrows or closes an answer, and each answer is its own conversation that never sees another answer's text. Only the owner sees the record.
- Reactions, rule changes, and other authorization epochs do not create a new Honcho workspace or re-ingest the archive. A correction deletes only the affected Honcho sessions and the conclusions Honcho derived from them, then writes the still-valid evidence again.
- Recall resolves the requested entity first and expands through relevant authorized relationships in bounded batches with cycle detection and deduplication. It preserves the 20,000-character prepared-context ceiling, reports partial results, and explains included paths such as a contextual mention. Permission is checked before exposing an entity name, relationship, count, path, source, or recalled content; traversal and project membership never grant access.
- Nocheh is the sole Honcho ingestion writer. Source, revision, audience, session, and chunk receipts support reconciliation. An uncertain write is reconciled from evidence; absence of confirmation is not permission to resend blindly.
- Every Honcho reasoning or embedding attempt is bound to a current authorized workspace and prepared representation. Retired workspaces and unbound jobs fail closed. Agent processes do not receive Honcho credentials or a direct route around the Nocheh gateway.
- Attachment and detachment are explicit owner operations. Attachment requires accepted live reasoning, embeddings, ingestion, retrieval, restart, and failure checks. Detachment preserves source data, owner edits, and receipts.
- Reattachment rebuilds previously learned sources in the selected representation. Optional catch-up includes consented sources received while detached; optional history includes older consented sources. Neither option grants learning consent.
- Outages and rebuilds expose limited-memory status while preserving available current context, native notes, and archive search. The status reaches the agent and the dashboard; a reply never carries it as added text. Honcho memory can be rebuilt from owned sources and receipts.
- The owner can re-run Honcho memory, and can replace Honcho memory with a new one, from the dashboard. Re-running and replacing never bring a retired message back into memory.
- Incremental synchronization reports its progress separately from memory availability. Previously ready memory in the current authorized workspace stays available while new sources are processed; initial builds, replacement workspaces, and actual recall failures report limited memory.
- A Honcho workspace becomes ready only after its Nocheh ingestion receipts and current-workspace derivation work finish without terminal queue errors. The readiness check obtains a workspace-scoped, read-only failure signal without exposing queue payloads or error text. Terminal derivation errors keep that workspace unavailable with an explicit failure status; a processed-with-error task is not successful memory. Previously ready context remains governed by its existing authorization and freshness rules while new work is building.
- Audience-filtered entity search, detail, relationships, evidence, uncertainty, correction history, and partial-result status are available under `/v1/entities`. Owner-only controls confirm or reject project suggestions, confirm or undo person links, and correct claims or relationships through the same revision-checked, idempotent commands used by chat and the dashboard. Ambiguity that affects an owner-private request prompts clarification; other ambiguity is queued quietly for dashboard review. Group conversations cannot confirm identities or change owner policy.
- Owner list pagination is omitted when all results fit on one page. When more pages exist, previous and next actions remain balanced around a clearly identified current page.
- Complete portability, coordinated backup, inactive restore, and reset account for entity identities, decisions, relationships, history, peer mappings, and ingestion receipts. Rebuilds create a new mapping version from owned evidence and retire earlier workspaces without deleting originals, owner corrections, or historical receipts.

<area name="Providers">

- Nocheh's services do not include CPA (CLIProxyAPI) or its admin panel. Model calls go only to providers configured in Settings.
- Nocheh settings has a provider feature that lets the user choose existing providers like GPT, Anthropic, etc., or a custom provider such as a hosted gateway by adding its URL and API key. Every provider is reached through the OpenAI-compatible API, except that replies and memory-notes reviews on Anthropic use Anthropic's Messages API, and a custom provider's address uses HTTPS. A custom provider's address works with or without its API version endpoint such as `/v1`: when the address names no version and has no model list as typed, the connection check tries it with `/v1`, and the address that answers is saved and used for every part. An address that answers as typed is used as typed. Provider API keys stay on the server, reach only the services that call that provider, and are never shown again after saving.
- One API key is enough unless the user wants to use a different LLM for each part, for example GPT for Honcho and Anthropic for Hermes. Everything is configurable: the user decides which provider and model each part uses. The parts are replies (Hermes), memory reasoning (Honcho), literal secret detection, and memory embeddings. One default provider and model serves every reasoning part unless a part names its own. When the secret check names no model of its own and runs on Anthropic, it uses Claude Haiku 5.5 (`claude-haiku-5-5`), a small, fast model; on any other provider it uses the default model. The owner can choose another model for it. Embeddings name their own provider.
- A fresh installation has no provider until the owner adds one in Settings. A part without a provider makes no model call: its work waits with the reason `provider_not_configured`, the dashboard says so, and the work resumes once a provider is saved and applied. No provider or model fallback is used: a part sends its requests only to its chosen provider and model.
- Settings › Models lists the providers, their key status, and each part's provider and model. The model list loads dynamically from the added providers: every model choice, the main model included, is a dropdown of the models an added provider lists, loaded as its address and key are entered, before saving, with a way to try the check again when the provider can't be reached; a saved key is sent only to that provider's saved address. The owner can also type a model name. A provider that a part uses cannot be removed. Applying a change restarts the services whose provider or model changed, including Honcho. Every reviewed embedding model stays selectable. Once Honcho memory holds vectors from one embedding model, choosing another asks the owner to confirm a memory rebuild first; applying the confirmed change switches Honcho to the new model and replaces long-term memory from the archive, and an unconfirmed change is refused.
- Each provider has at most one credential, with no provider/model fallback, quota switching, or additional proxy request retries.
- Model calls use the provider's prompt caching wherever a prompt starts with a reusable part long enough to be cached, such as an agent turn's tools, instructions and history. Anthropic's OpenAI-compatible API has no prompt caching, so calls that can be cached use Anthropic's Messages API. The Usage page shows the cached share of input.
- Every voice note, audio file and round video is transcribed, whether it arrives live, comes from an import, or was saved before transcription was set up. Nocheh calls a ready transcriber (Hermes's own, which converts, trims and splits recordings) with the provider and model chosen under Voice notes in Settings › Models; OpenAI with the existing key is the default, an exception to the Anthropic-only rule for transcription. The transcript goes through the secret check like typed text, and the original audio is kept. A reply waits for its voice note's transcript; a busy or unreachable provider is tried again, and a recording that cannot be transcribed records why and never holds a reply. Without a provider key a voice note is archived only, records that transcription is not available, and is transcribed a few at a time once a key is added. Each transcription's audio length and cost show on the Usage page, and an import shows what transcribing its voice notes costs before it starts. Every recording is transcribed whole, whoever sent it: someone who may not talk to Nocheh in a group gets the same full transcription as the owner.
- Honcho has separate budgets for paid embeddings and memory reasoning. Paid embeddings have a $5 total pilot cap, followed by an owner-configurable cap per UTC calendar month starting at $5. The Honcho dashboard lets the owner change that embedding cap from $0 to $15 in cent increments after accepted attachment; $0 pauses new paid embeddings. Honcho reasoning uses the memory part's provider, consumes no embedding dollar cap, and has its own 1,500-request safety bound per budget window. Embedding requests do not consume the reasoning request bound.
- A durable embedding admission ledger reserves the configured model's upper-bound hold before each bounded API request: $0.01 for `text-embedding-3-small` or $0.02 for `text-embedding-3-large`. Successful calls with valid reported token usage settle against the cap at the model's token-priced amount, rounded upward to a microdollar. A definite upstream HTTP error releases its admission hold from the cap; transport failures without a confirmed response, unfinished calls, and successful calls without reported usage retain their conservative hold. Historical monthly failed calls whose response type was not recorded remain explicitly labeled unverified and visible in the ledger, but their holds do not count as confirmed spending or block the monthly cap. The exhausted pilot's historical holds remain counted. The ledger reports original and released holds separately and never represents its estimate as a provider invoice. Settling existing successful monthly calls preserves the exhausted pilot's historical accounting. The ledger cannot reset through restart, restore, a cap change, or repeated monthly activation. Lowering the cap below existing accounting blocks new paid embeddings without erasing existing entries.
- After a paid embedding request fails with an upstream 5xx or transport error, Honcho's egress blocks new paid admissions for a durable, shared cooldown of at least 60 seconds, doubling after consecutive failures up to one hour. Calls during cooldown receive a transient response with a numeric retry delay and create no new spending reservation. A successful request admitted after the latest failure clears the cooldown; an older in-flight success cannot clear it. Memory reasoning remains independent. Failed requests retain their original admission records; only failures with uncertain delivery retain a hold against the cap.
- The Honcho dashboard presents distinct embedding dollar-budget and reasoning request-limit sections. The embedding section shows the adjustable monthly limit, amount counted toward the cap, remaining admission headroom, embedding requests, reported tokens, and an estimated embedding cost. It identifies the estimate as distinct from the provider invoice and makes missing usage reports visible. The reasoning section shows reasoning requests and remaining request allowance without implying API dollar charges. Only an authenticated owner can change the embedding cap, with revision-checked, retry-safe updates.
- When exhausted pilot reservations block Honcho's required live acceptance, an explicit owner command can activate the $5 UTC-monthly cap while memory is detached and unverified. That spending transition does not verify or attach memory, permit historical ingestion, or bypass the live acceptance gate.
- The embedding provider and model are explicit configuration: OpenAI by default, or another OpenAI-compatible provider from Settings that serves the same reviewed embedding models. The default model is `text-embedding-3-small` with 1536 dimensions; selecting `text-embedding-3-large` also uses 1536 dimensions. Vectors from incompatible models are not silently mixed; model changes require rebuilding affected memory. The paid key is confined to the metered boundary.

<area name="Monitoring">

- LLM speed has measurable timing metrics, distinct from local workflow waiting and processing. Performance assessment accounts for the owner machine's resources, network conditions, and GPT/LLM response time. To address slowness, the duration of each stage is broken down: system workflows are tracked by execution time, and the response times of external (third-party) services and of the LLM are measured separately. Monitoring shows both average stage times across recent messages and a per-message stage breakdown. Metrics identify their measurement boundaries; combined network and provider time is not labeled as isolated model computation, overlapping phases are not added as independent durations, and unavailable measurements are not reported as zero. Timing telemetry excludes conversation content and credentials.
- The owner can inspect event-bound timing evidence through the admin CLI, including provider response waits, local guarding and forwarding, workflow receipts, and unavailable historical measurements. Failed attempts preserve available timing evidence without claiming completion.
- Service monitoring identifies each tool, purpose, host/container location, and expected running, completed, optional-stopped, or unhealthy state. API, capture, and Inngest connectivity are reported independently; process availability does not establish processing progress.
- Nocheh monitoring exposes observed Telegram polling progress and incidents, recent workflows, retries, waiting, success, skips, failures, uncertain delivery, provider routes, and service state. A fatal polling failure cannot remain reported as connected; retryable fatal adapter failures enter supervised recovery.
- Internal API keys are labeled with their service name and usage. Monitoring shows each part's provider and model, and a part without a provider as not configured, without exposing keys.
- Nocheh has its own usage tracker and does not depend on CPA for usage. Each part's usage is tracked separately, by part, provider, and model. Where Honcho and Hermes handle tracking, Nocheh uses those, and Nocheh calculates the remaining metrics itself. Everything is displayed in one place, the Nocheh dashboard, so the owner does not have to check multiple sources to see usage across different areas. The tracker keeps counts, never message content. A cost Nocheh cannot price is shown as unknown, never as zero. Where Hermes has no price for a Claude model on the Anthropic provider, Nocheh prices it from Anthropic's list prices, including runs recorded before; a Claude model behind another provider, such as a gateway, stays unknown, since it may bill differently.

<area name="Runtime integration">

- Nocheh's own `nocheh-telegram` service is the Telegram bot and the only holder of its token; the brain returns replies and never sends to a platform. Hermes supplies the agent, tools, profiles, sessions, and built-in memory. Custom integration stays thin; minimal pinned compatibility patches support mandatory enforcement.
- The brain reaches Nocheh's data, the archive, memory recall and search, tasks, Notion, message and operation requests, background jobs and knowledge proposals, only through the tools Nocheh serves over MCP at its own internal `/mcp` endpoint, as the server `nocheh`. Only a turn's own pass reaches them, and each call passes the same checks as the route it uses. The tools never name the memory engine behind them. A refused call answers with its reason as ordinary tool output. Each turn's pass names the brain it is for.
- The brain sits behind one brain socket inside Nocheh. Nocheh starts, observes, cancels and follows each turn, and reaches the brain's own settings, role and skills, notes and scheduled tasks, only through it. The brain never sends anything to Telegram or another platform: it returns its reply, or chooses silence, and Nocheh delivers. One brain runs at a time; Hermes is the only brain today, and another, such as Claude Code, can replace it without changing Nocheh's data, rules or front doors. The dashboard shows which brain is plugged in and what it can do; a page for a feature the brain lacks says the connected assistant can't do this.
- Native protocols and identifiers remain behind the brain socket and capability-checked helper service operations. Native pages and operations use actual runtime state; unavailable capabilities are explicit.
- Telegram, browser, and scheduled turns use the same managed capture, audience, guard, and tool-policy boundaries. One supervisor owns Telegram polling and scheduler lifecycle. Profile locks prevent concurrent native-memory and conversation writers. A busy profile defers work before execution; waiting preserves the same execution identity and remains cancellable, with current permissions checked before admission.
- Selected conversation messages are processed in order. A failure before Telegram delivery begins remains retryable under a fresh attempt identity; an interruption after delivery may have begun remains an uncertain terminal effect and is never automatically resent. One slow or failed turn does not silently discard a later captured message.
- Messages in different chats are processed in parallel. Topics in one group get answers at the same time instead of waiting in line. Messages in one private chat, one group's General chat, or one topic keep their order. The reply limit (chats answered at once, three by default) and process parallelism (isolated agent runs at once, shared by replies, memory reviews, browser turns and schedules, four by default) are configurable from Nocheh settings. The reply limit never exceeds process parallelism. Secret-guard checks of different messages also run in parallel; how many run at once (three by default) is configurable from Nocheh settings, and one message is never checked twice at the same time. Secret-guard checks for replies go ahead of checks for background memory learning.
- When Telegram answers every transmitted attempt of a reply with a definite error, such as a deleted topic or a blocked bot, the reply was not delivered: it is recorded as rejected by Telegram and is not retried automatically. A rate-limit rejection remains retryable.
- A documented Telegram rate-limit rejection honors `retry_after` before a bounded new send attempt. Every attempt retains its durable receipt and current audience authorization. Confirmed delivery and uncertain delivery cannot be repeated as rate-limit recovery.
- In ordinary Bot API chats, Nocheh does not claim automatic detection of message deletions. Telegram Business deletion updates apply only to connected business accounts; ordinary message deletion requires the owner's retirement action in Messages. Reaction delivery in groups requires Telegram admin rights and explicit update subscription, and anonymous counts may arrive late. Nocheh covers its owner DM and selected groups without an MTProto connection.
- When the agent is working, Telegram shows the bot's typing status in the chat or topic it is answering, renewed every few seconds so it stays visible until the reply is sent or the turn fails. It appears only for a turn that will actually write a reply: never for someone Nocheh does not serve, a group message that did not address it, or a fixed reply that needs no model. The status passes the same audience and permission checks as the reply, is not recorded as a delivery, and the owner can turn it off in Settings › Telegram.
- The bot can add reactions to users' messages using Hermes's built-in feature: while the agent works on a message, the bot reacts to that message with 👀, then with 👍 once the reply is sent or 👎 when the work failed. A turn that ends without a reply, is cancelled, or whose delivery is uncertain removes the 👀. Reactions appear for the same turns as the typing status, pass the same audience and permission checks, are not recorded as a delivery but, like every send, leave a send record without content, and the owner can turn them off in Settings › Telegram.
- Nocheh records every action it sends to a chat app such as Telegram or Slack: messages, edits, cards, button answers, notices and reactions, and the sends Nocheh's own checks held back. Each record shows what kind of send it was, to which chat (the app's chat, thread and message ids as the app writes them, and the Nocheh chat), when, and whether it worked: sent, refused by the app, uncertain (it may have arrived), or not sent by Nocheh, with a short reason code. A record never holds message text, buttons, links, credentials or the app's own error wording. A button answer that opens the asker's private chat, as Answer privately's does, is recorded as a button answer, without its link. The "typing…" status is never recorded, not even when it fails, because it fires constantly. A record is only a log: it is not a delivery receipt and never decides whether something is sent or sent again. Telegram, Slack and any later front door keep the same record. The dashboard shows the records in System › Sent to apps, including the failed ones. A try that failed but was sent on a later try within 15 minutes, an edit that changed nothing, an expired button answer, a reaction the chat does not allow, a leave that found Nocheh no longer in the chat, and a leave try whose group Nocheh has since left for the same add, a refusal at an upgraded group's old id included, are listed but not counted as failures.
- Telegram replies express source attribution in ordinary language and do not show raw internal `nocheh:event:` identifiers. A group reply cannot disclose private source content or private source identity through a citation.
- A complete durable runtime journal with assistant progress and no delivery-stage event may reconcile a legacy interrupted Telegram receipt from uncertain to retryable. Missing, incomplete, malformed, or delivery-stage evidence never authorizes an automatic resend.
- Background native memory review waits for a short quiet interval after foreground activity so immediate follow-up messages can use the profile. Waiting does not consume an execution attempt or replace existing review receipts.
- Nocheh keeps a chat's history when its memory updates, including a new guard epoch from hiding, restoring, correcting or automatically learning memory: the chat continues with its recent messages and delivered answers, and hidden messages stay out. Earlier copies of the chat's history are removed once they have been unused for 15 minutes, so hidden content does not stay behind in them. This holds the same whether the chat was last used from Telegram or opened in the native dashboard. A chat's history, its Hermes profile and notes continue under its Nocheh chat id, so a group Telegram gives a new id keeps them.
- The native Hermes dashboard's naming makes clear what each entry is: each profile is listed by the chat it belongs to, the owner's private chat or the group's name, and the owner's private chat appears once; each Telegram conversation in Sessions is titled with its chat's name, and background memory reviews are not listed as sessions. Each private answer has its own profile, listed in Memory › Notes as a private answer, named by where it was asked, as its first line names it, and the day it ran, and never as the owner's private chat, and its conversation in Sessions is titled “Private answer”. A private answer's profile and its conversation are removed once they have been unused for two hours, when no answer can arrive in them any more.
- Browser input defaults to owner-private scope; explicit group selection remains group-scoped through capture, tools, sessions, and memory. Reconnect and resume reuse stable stored identities and profile-bound sessions without duplicate submission.
- Durable claims, leases, heartbeats, and result receipts distinguish completion, interruption, and late evidence. Lost responses are reconciled; abandoned work is not automatically rerun as a new external effect.
- The brain socket provides asynchronous `startTurn`, `turnEvents`, `observeTurn`, and `cancelTurn` for Telegram, browser, scheduled and background channels. Resume reconciles the same execution identity and preserves browser streaming, reconnect, cancellation, and session identities.
- In group chats, Nocheh does not answer every single question that comes up. A question might be directed at the entire group or a specific individual, so Nocheh responds only when personally addressed: a reply to one of its messages, a mention of its @username or a tap on its name, or its name at the start of the message. Its name is its Telegram display name or any name in the owner's “Names that address Nocheh” list. That list starts as “Nocheh” and “نوچه”, and the owner can change, add, or remove names. Every group message is still captured whether or not it addresses Nocheh. When Nocheh replies in a group, it knows what was just said there: the reply sees the group messages since its last turn in that conversation, including messages that did not address it, with who wrote each one and when. The owner can instead let Nocheh answer every message from the owner and the members who talk to Nocheh there; “Group replies” and “Names that address Nocheh” appear inside the Telegram section of Settings, and only when addressed is the default. Intentional silence is a valid captured outcome. Group participants cannot approve actions or change administrative, provider, privacy, or guard settings.
- A forwarded message is someone else's words unless it is the sender's own earlier message, and a message sent through an inline bot is that bot's words. Its turn knows, from Telegram's own record, where it was forwarded from, also when it is among the recent group messages a reply sees, and treats what it says as information the sender shared, not as their request. Text inside a message cannot write a line that reads like the ones Nocheh puts before it. A forwarded command, or one sent through an inline bot, never runs, even the owner's own, and gets a short fixed answer. Memory keeps it that way: a note drawn from it is labelled as coming from a forward, and long-term memory keeps it with the owner's forwards and files, not as the owner's words. Someone else's message the owner pins is kept the same way.
- An assistant answer succeeds only after confirmed native completion with a nonempty text answer or an explicit intentional-silence result. Missing, blank, malformed, failed, or interrupted model answers cannot be recorded as successful silence or replaced by a memory-status notice. Pre-delivery failures remain recoverable under the existing receipt and retry rules.
- In each selected Telegram group, only the owner and the group's members may address Nocheh. Only the owner and the members who may talk to Nocheh there can start a bot response or tool-using turn, and what a member asked for is checked against that member again just before it happens: a reply before delivery, a message it sends, a web page read or outside tool, a job, before each part of its report too, and a task change. The owner manages members in the dashboard only, on the Members page; group participants cannot administer them, and no setting lists them. Members are allowed by default in the groups they are in, and the owner has an option to control a member's access: a permission scope per member, like Telegram's group permissions.
  - “Talk to Nocheh in groups they joined” is on by default. Under it, each on by default and each off while it is off: “Small jobs (no daily limit)”; “Post to their other groups”, where the member confirms each post with a card; and “Web pages and outside tools (no approval)”.
  - One “Tasks: read and write (or read only)” setting, read and write by default, for their groups and the members' app alike: task access is data access. With read and write a member adds, reads, changes, trashes and restores the tasks they reach, other people's included. A member whose tasks are read only lists and reads the tasks they reach and changes nothing. Under it, “Reminders to themselves”, on by default, works only with read and write: off, the member sets no new reminder, in a group or in the members' app, and can still remove their own.
  - Each of a member's groups has its own switch. A group the owner never switched off for a member, a group they join later included, is on.
  - “Pause this member” stops everything the member can do in every group until the owner turns it off; Remove takes the member away.
  - A member's first message in a group is enough to talk there. Whatever Nocheh does for a member in a group without a message from them there, such as a post into it from another group or a job of theirs running there, waits until Telegram has shown them in that group, and stops once Telegram says they left.
  - Each member has a daily message cap, 200 by default, which the owner sets from 1 to 10,000 on the Members page: the turns a member starts in a UTC day, across all groups and their private chat together. A turn past it is not started and uses no model, and the member gets a fixed reply at most once a day per group, and once a day in their private chat. The owner is never counted.
  - Every change to members applies at once, with no restart and no Apply.
  - Nocheh acts otherwise only for the owner and members: someone who may not talk to Nocheh in a group, a stranger or a member who is paused, has talk switched off or is switched off there, gets a fixed message in the chat when they address it, at most once a day per person and group, without starting a turn or using a model; a fixed message Telegram refused, or that never left, does not use up that day's. A post in a chat's own name, such as an anonymous admin's, gets nothing. The owner can edit both fixed replies in Settings with the other built-in texts.
  - The owner is never a member: the owner's Telegram user ID cannot be added as one, and the Members page warns when the owner's account is linked to a member, which then counts for nothing.
- A member can also talk to Nocheh in their own private chat with it. “Private chat with Nocheh” is a switch per member, on by default; a member who is paused or removed, or whose private chat is off, gets the same fixed private message as a stranger. Group talk switched off does not stop private chat.
  - A member's private chat only reads: that chat, and the groups the member joined, across projects and groups in no project. It never posts, sends, starts jobs, opens web pages, uses outside tools, asks for actions, changes tasks or keeps notes of its own, and it never reads another private chat or what the owner or anyone else said privately. Members see their groups' tasks there too, read only, one project's list at a time.
  - A group the member joined counts only while Nocheh is on there, their switch there is not off, and Telegram has shown them in it within the last 30 days. Before a private turn, Nocheh asks Telegram again about a group it last confirmed more than 6 hours ago, and in the places left about a group it has not confirmed for 30 days, at most 10 a turn; a group Telegram says they left is no longer read, and a group Telegram says they are still in is read again. A group past those 10 is not read on that turn, by the turn or its tools. When Telegram does not answer, a group not confirmed for 30 days is not read: unknown fails closed. A joined group is read with its whole history.
  - What a member may read is checked again on every read and tool call, so a pause, a removal, private chat switched off, or a group left or switched off applies to the next one; a reply built on what the member may no longer read is not sent.
  - A member's private chat never reaches a group, another member, the owner's own turns, learning, long-term memory, the owner's notes, grants, suggestions or sharing previews, whatever the owner confirms. It is never a sharing rule's source or destination. A member who asks who can see the chat is told truthfully that the owner can read it. A member's turns run one at a time, in their groups and their private chat together. A member's turns waiting on each other never hold up the owner's turns or other members' turns in a group.
  - When the owner's own message in the owner's private chat, not a forward, names a member by the name Telegram shows for them and asks what they said to Nocheh privately, Nocheh answers in a separate message in the owner's private chat that names that member's chat as its source and reads only that chat. That answer is then dropped: it is never learned, never kept in the owner's ongoing conversation, and the owner's later turns cannot read it or a quote of it. When the answer cannot be given, because the chat closed, the member was removed or the time ran out, the owner gets one short notice instead, once.
- Only the owner adds Nocheh to groups. A selected group is a group Nocheh is on in, and which groups those are is never a setting: the owner's own add turns Nocheh on in a group, and the owner turns it on or off there in Chats. When anyone else adds Nocheh to a group, a member, a stranger, another bot, or an admin who remains anonymous, Nocheh stays silent there and leaves. A member's add sends the owner one line naming who added it, saying that only the owner can add Nocheh and that the owner can add it there; an anonymous add sends one line saying to turn off Remain anonymous and add Nocheh; anyone else's add sends nothing and keeps only a record with no names or message text. When Telegram does not let Nocheh leave, or keeps answering for over an hour that the group was upgraded, it stays silent there, and the owner's line, when there is one, says so. The owner gets at most one such line per group a day and at most ten such lines a day in all. A group Nocheh is already in that the owner never turned on stays silent and is listed as Off; Nocheh never leaves it on its own. Telegram upgrading a group to a supergroup is never an add: a group the owner turned off stays off, and a group Nocheh is leaving is still left, also when the new supergroup is kept as a chat of its own. A member switched off in the group is switched off in the new supergroup too, also when it is kept as a chat of its own. The owner's own add still counts in a group Nocheh had only just seen and had no add for. Once the owner's card said Nocheh is on in the new supergroup, Nocheh never leaves it. Nocheh acts only on adds and removals that arrive after it starts following adds; older ones in the archive are kept in the record only. When someone removes Nocheh from a group it was on in, the owner gets one line, which those limits never hold back and which does not count toward them. A data reset that keeps the owner's setup brings back a group Nocheh was still leaving, with its topics, as Off. Members and their switches for a group stay when Nocheh is turned off there or leaves, for when it is on there again. Messages from a group Nocheh leaves stay in the archive like any chat Nocheh does not serve.
- Hackers can't inject a prompt or a file into the system. Someone Nocheh does not serve is anyone who writes to it in a private chat other than the owner and the members who may talk to it there, and anyone in a group or channel the owner has not selected. Their messages are kept as received for the owner to see in the dashboard, but their files are never downloaded, no model checks or reads what they sent, nothing is learned from it, and the assistant never sees it, including in the owner's own search and conversation lists, where chats they named stay out. When the owner starts Nocheh from another Telegram account, it does not receive or act on those messages and cannot see a menu: nobody sees a Telegram command menu for Nocheh. Anyone who writes to Nocheh privately and may not talk to it there, a stranger or a member who is paused or whose private chat is off, gets one fixed message, at most once a day per person, without starting a turn or using a model; the owner can edit it in Settings with the other built-in texts. The dashboard marks such messages as not allowed.

<area name="Role and skills">

- The owner can set a role and skills per chat: one group or user uses one role and skills, and another chat uses another role and skills. A chat here is a selected group or the owner's private chat, and it keeps its role and skills when Telegram gives it a new id. A member's private chat has no role and skills of its own: it uses the default for groups. Topics are not covered: a topic uses its group's role and skills. A private answer, though Nocheh writes it in the owner's private chat, uses the role and skills of the asking group's project, else the default for groups, and never the private chat's own role, skills or default.
- Nocheh uses the Hermes profile's own role and skills instead of implementing them in Nocheh: a chat's role is its Hermes profile's `SOUL.md`, and its skills are Hermes skills in that profile's skills folder. The owner's private chat has its own default role and default skills, and groups have theirs; the private chat's default never loads in a group or any other chat, and any turn that is not the owner's private chat uses the default for groups. The default for groups starts empty. A project can have its own role and skills for every chat in it. A chat's own role replaces its project's role, which replaces its default role; skills add up from its default to the project's to the chat's, and a skill with the same name as an earlier one replaces it in that chat. An archived project's role and skills no longer apply.
- A saved role or skill applies from each affected chat's next turn, including conversations already under way, which keep their history; Hermes' own prompt refresh rebuilds their instructions.
- Role and skills are set by the owner only, from the dashboard: on each chat's page in Chats, on each project's page in Memory › Projects, and the two defaults, for the owner's private chat and for groups, in Settings › Assistant. The agent reads a skill when it applies but cannot create, save, or change a role or skill, and group participants cannot change them. Only memory can be updated by the agent: each chat's memory is its Hermes native notes (`MEMORY.md`, `USER.md`); Nocheh adds no separate memory file.

<area name="Workflow orchestration">

- Inngest is used for the full Nocheh workflow, not just part of the system; the Nocheh core runs on Inngest. Hermes and Honcho are parts of that workflow. Hermes' own internal workflow does not use Inngest.
- All product workflows use local Inngest: Telegram attachment retrieval, guarded preparation and dispatch; confirmed imports; native memory review and Honcho synchronization, rebuilding and reconciliation; browser turns; scheduled occurrences; organization; and approved actions. Synchronous security checks and the native agent's internal reasoning loop retain their own boundaries.
- Inngest and persistent Redis run in the installation's Docker Compose project. Inngest has a dedicated database and role in the existing PostgreSQL instance, separate from the owned archive. TypeScript Connect workers have distinct application and executor identities and versions; Python adapters remain thin. Inngest Cloud is outside this Compose workflow architecture.
- `nocheh-app` initializes the dedicated Inngest database and role before becoming healthy. Initialization preserves existing data and runs safely on repeated startup; no separate database initialization service is required. Inngest starts after the application and Redis are healthy, while application startup remains independent of Inngest availability.
- Fresh installations use isolated Hermes execution, the shared provider route, and evidence-based memory context; saved provider credentials and accepted cutovers retain their boundaries.

Legacy runners and engine-switch controls are absent. Synchronous security and native tool internals retain their own execution boundaries.
- Source capture and relevant state changes have a durable, recoverable handoff to workflow requests outside the archive database. A crash between source persistence and workflow scheduling cannot lose required work or duplicate an external effect. A supervised publisher retries delivery independently of Inngest. Source capture and spool draining continue during orchestration outages.
- Inngest events, step outputs, errors, and logs contain only opaque IDs, versions, counts, timestamps, and allowlisted status codes. Messages, transcripts, prompts, results, tool arguments, and credentials stay in protected stores and are resolved inside executing steps.
- Nocheh owns the workflow registry linking source/job IDs, workflow versions, Inngest runs, attempts, and receipts. Permanent deduplication does not depend on Inngest's finite event-deduplication window. Each workflow family has one fenced execution authority.
- The organization workflow defers owner-turn proposals until confirmed turn completion and enqueues live-learning proposals after learning completes, including completion recovery. Automatic application uses the foreground-reply publication check and waits while replies are active. Owner revocations retain their immediate enforcement path; organization does not disrupt a foreground reply by invalidating its memory mid-turn.
- Retention of Inngest's run history and telemetry (events, run and finish records, event batches, spans, history, traces, trace runs, and disconnected worker connections) is configurable and adjustable in days. By default (`0`) Nocheh keeps those records forever. When the owner sets a number of days, records of runs with no activity for longer than that are removed automatically; an event is kept while a run it triggered is kept. The same setting removes Nocheh's workflow publication records and Inngest run links of superseded dispatches and of workflows closed for longer than that, broker model-call security events and guard invalidation notes older than that, and superseded Honcho context summaries that no current memory generation serves. Security events of actions and tools remain the owner's audit and are not removed by this setting. Retention checks run daily, when the database starts and then once a day. Retention never removes Nocheh's receipts, workflow registry, or Inngest queue state.
- Hermes keeps finished delivery logs (outbound send journals, dispatch receipts, and the request, event and result files of finished runs) forever by default (`0`). The owner can set a number of days from Nocheh settings, after which finished logs are deleted. A delivery or run that has not finished, and a run result not yet handed to Nocheh, is never deleted. The records of what Nocheh sent to chat apps follow the same setting.
- Inngest owns retry timing. Prerequisite waits are distinct from failed attempts; profile locks and bounded concurrency apply. Current audience, guarded revisions, import consent, and permissions are checked before execution. Terminal, cancelled, denied, suppressed, and ambiguous outcomes cannot automatically restart. Lost responses and uncertain effects require receipt reconciliation, never blind replacement execution.
- Telegram processing and delivery form one receipt-protected native runtime operation with separately visible assistant and delivery progress. Stored transcripts and guarded revisions are reusable. Intentional silence is a valid outcome; uncertain sends stop for reconciliation.
- Confirmed imports use bounded checkpointed batches, preserve upload validation, mapping, identities, progress, cancellation, and explicit learning consent across retries, and send no historical replies. Source preparation, owner edits, consent, and memory generation changes request the appropriate follow-up work. Honcho execution requires its existing attachment and acceptance gates.
- Workflow list/detail and validated retry/cancel operations are available at `/api/nocheh/workflows` and through the CLI, preserving existing job IDs, browser protocols, and compatibility routes. Nocheh shows family/status filters, stage, attempts, next retry, waiting reason, timestamps, source links, outbox backlog, oldest waiting work, connectivity, and stale observations with accessible status text and ten-second refresh.
- Nocheh Monitoring opens with a compact operational summary: running, waiting, failed, last recorded success, and backlog, with expandable details and an obvious link to the workflow scheduler's own console. Summary totals cover all workflow families independently of history filters and pagination. Unavailable or stale observations and uncertain outcomes stay visible in the compact view.
- The Monitoring summary breaks waiting into queued and condition-bound work, shows the leading waiting reasons and workflow families with the oldest waiting record, and explains that one source can produce several workflow records. Denied or rejected closed outcomes are distinct from failures and uncertain effects.
- The detailed Inngest UI is inspection-only behind the Nocheh owner session; execution controls use Nocheh authorization. Monitoring distinguishes retryable and terminal failure, waiting, intentional skip, cancellation, and uncertain effect. Nocheh sends no workflow notifications outside the owner's own Telegram private chat.
- The owner gets notice about each failure and issue, so the owner can fix it: failed and uncertain background work, a service, worker or Telegram connection that stopped working, a part with no model, incoming messages that could not be saved, backups and off-site copies that did not finish, were skipped for low disk or left out files a command made unreadable, files a reader could not read because Hermes's memory space was full or a write was refused, sends to chat apps that failed or were never answered (a failed send of a notice itself, such as a problem notice, task reminder, import message or inbox list, shows in System › Health but never causes a notice), failures to tell where a memory note came from, reads of long-term memory that came back without the owner's forwards and files or memory context, and model calls that failed, including calls the model refused and texts the secret check hid because the model refused to check them. A notice about failed model calls says why they failed, such as refused by the model, over the provider's limit, took too long, or a provider error, with the exact error the provider sent where it is known, such as overloaded with its HTTP status, so the notice is clear; a run the assistant stopped itself, such as after repeated errors, is named as such and not as a provider error. System › Health says the same. Only codes are kept, never the provider's message or any content. A call stopped at its time limit counts as failed too. Each notice goes to the owner's private Telegram chat as one message listing what is new or worse, and System › Health lists the same problems. The same problem is repeated at most once an hour, and only when it got worse; past failures already kept in the history are not announced again. A problem counts as cleared only when the check could read it, and failed tasks only when two checks in a row find fewer, so a task that is being retried is not counted as cleared. If it returns within the quiet hour, when no new notice may tell about it, the ✅ line is taken back and the buttons return; after that hour it gets a new notice. A line about an earlier UTC day's model calls stays as sent. The owner can turn the notices off in Settings › Telegram and edit their wording in Settings; they are on by default.

<area name="Owner tasks and the Telegram mini app">

- Nocheh has its own local task manager. Tasks are Nocheh's own data, kept with the owner's other data rather than in an outside service. The owner adds, lists, finishes, drops, reopens and edits tasks from the dashboard and by telling Nocheh in the owner's private chat; both edit the same list. A task has a title, optional notes and an optional due day.
- The task structure is like Notion and other task managers and covers all their domains, so later features do not change stored tasks. A task has a status from the owner's own list, each status being one of four kinds (not started, active, done, cancelled); a priority from five levels whose names the owner sets; an optional start and due day, each with an optional time; an optional repeat; reminders; subtasks; tasks it waits on, is related to, or duplicates; who it is assigned to, separate from the people it is about; a manual order; the owner's own columns, like a Notion table database, each private to the owner unless the owner shares it with project chats; comments; links and archived messages; Markdown notes; and who created and who finished it. Every change is kept in the task's history. Finished tasks can be archived, and any task can go to the trash, be restored, or be deleted for good from there. Each task has room for its ID in an outside tool such as Notion.
- A reminder goes to whoever set it, at its set time, sent once: the owner's to the owner's private chat, and a member's to that member's own private chat with Nocheh. A reminder in a member's chat shows the task's title, due day, list and notes and says that they set it themselves; it never names who else wrote or closed the task, or where. Each reminder stores who set it, the owner or a member, and where, the members' app included. In the owner's private chat, a reminder set anywhere but by the owner in the private chat or the dashboard gets a fixed “Set by … in …” line, and a reminder on a task whose title, notes or due day someone last wrote elsewhere, or that a person closed, gets fixed lines saying who and where. These lines come before anything a person wrote: the task's title shows on one line and each line of a person's notes is marked, so nothing a person wrote can pass for them. Reminders that people set, that go to the owner's private chat and that come due together in one group are merged into one message, with at most one message per group every 10 minutes, so with many due at once each further message for that group comes 10 minutes after the one before; there is no daily cap, and no reminder is ever dropped. The owner's own reminders arrive at their set time, one message each, also on a task a person finished, archived or trashed, saying who closed it; when a repeating task's next one holds the owner's reminder at the same minute, that time comes once, from the next one; a task the owner closed gets no more of the owner's reminders, and a person's reminder on a task closed before it came due is not sent. A reminder is never refused for its length or for a character cut in half; one that Telegram refuses shows as Not sent on the task and in System › Health, and the reminders after it still arrive. When the owner's own message in a group removes reminders that were set elsewhere, the owner's private chat gets one notice naming them. Its wording, the lines that say who set it and where, statuses, priority names, columns and the time zone used for Today and Upcoming are editable from the dashboard.
- The owner sees tasks as a list, as cards, or as a board by status, and has Today and Upcoming views. A calendar view and saved views come later.
- Tasks are flagged by scope and tags. Life and personal tasks are separate from projects, and each project has its own private scope and list. Tasks point to the project, the group and the users (people Nocheh knows) they belong to, and have additional tags: a list of tags, like a Notion table database, not a single domain. Inside a project, a task's group decides who sees it: a task set on the project itself is seen by every group of the project, and a task that belongs to a group or topic only by that group, or only by that topic when the group's topics keep what they know apart.
- The owner reaches every list from the dashboard, the mini app and the owner's private chat, and can move a task between lists. A group or topic that belongs to a project reaches, for everyone who talks to Nocheh there, only that project's list, and on it only its own group's tasks (every group's tasks of the project while it shares its group chats) (its topics' tasks too when they share what they know) and the tasks set on the project itself: it never sees personal tasks, another project's list, the names of other projects, or another group's tasks, their count, tags, links, parent or history. A group or topic that belongs to no project reaches no list, including when the owner writes there. An answer sent with "Answer privately" reads only the tasks of the groups it combines and the tasks set on their project itself, and changes none.
- A member's private chat with Nocheh lists and reads, and changes nothing in, the tasks of the groups the member may read there: one project's list at a time, each showing only those groups' tasks and the tasks set on that project itself, never a list of every project, never another group's task and never the owner's personal tasks. Asked without naming a project when there are several, it names the lists to choose from. A group in no project has no tasks there.
- Task access and edits work like data access for projects and groups. A member who talks to Nocheh in a project's group or topic manages the tasks it reaches there, adding, reading, changing and removing them, unless their tasks are read only. Such a member sets and removes the reminders people set on those tasks; a person's change never removes the owner's reminders, which stay when a person's list leaves them out. A reminder a member set for themselves in the members' app is theirs alone: no chat sees it or removes it. Each person, and the owner, keeps up to 10 reminders of their own on a task. A task added there belongs to that group or topic unless it is set on the project itself, and a subtask has its parent's list and group. That chat sees each task only as it is on that project's board: its comments and history only from when the task last joined that list or changed group, its links but never the archived messages attached to it or their labels, only its reminders still to come, only the owner's columns the owner shares with project chats, its group, also in its history, only when that chat reaches that group or topic, who made or finished it only when that happened on the list, and never its IDs in outside tools such as Notion. No project's chat, member's private chat or members' app sees who a task is about, the owner's own names for people or the values of the owner's person columns. It sees a person a task is assigned to only by their Telegram name, and only when the owner linked that person to a Telegram account that is in one of the groups it reaches; every other person assigned is only counted, as other people. A change made there never changes another group's task: moving, archiving or trashing a task there leaves another group's task under it where it is, no longer under that task. A change made there never removes what only the owner sees, such as the archived messages attached to the task or its links to tasks on other lists, and what the owner attached never limits what that chat can add. A task with no record of when it joined a list shows a project's chats no comments or history from before its next change or comment.
- Nothing on a task crosses from the owner's private side to a project's chats without the owner seeing first who will see it. From the owner's private chat, a change that a project's chats would see waits for a card in that chat: adding a task to a project's list, moving one into it or to another group in it, changing anything else on a listed task beyond its status, priority, start and due days and times, archive, trash and list (such as its title, notes, tags, people, assignees, repeat, reminders, links, attachments, columns, parent or the tasks it waits on, relates to or duplicates), or commenting on it. The card names the project and every chat that will see the task, or says that no chat sees it yet; for a task set on the project itself, says that chats added to the project later will see it too, and for a group's task, that the project's other groups don't see it; says what stays private; and shows the change exactly, including every task under a task that moves, which moves with it, archived and in the trash too. Only the owner's press decides it. Approving makes the change only while the task, the tasks under it, its list, its group and the chats that will see it are as the card showed, and otherwise says that nothing changed. A change too long for one card is not made from chat and is made from the dashboard. Moving a task into a project's list or to another group in it from the dashboard or the mini app names the chats that will see it and how many tasks under it move with it, and says what stays private and, for a task set on the project itself, that chats added to the project later will see it too, before it saves. Letting project chats see one of the owner's columns names the chats of each project's list and says that the values already in it show there, before it is saved.

When the owner moves a group to another project, its tasks and its topics' tasks on the old project's list move to the new project's list with every task under them that is not another group's, and the group keeps seeing them as before; the tasks set on the old project itself stay there. When a group leaves every project, its tasks stay on the old project's list, where only the owner sees them. Moving a group from one project to another says first that its tasks and its topics' tasks move with it; taking a group out of its project, from the project or from the group's page, asks first and says that they stay on the old project's list, where only the owner sees them.
- Nocheh has a Telegram mini app for managing Nocheh from Telegram. The task manager is in this mini app too. The mini app is another front end on the same owner API as the dashboard, not a separate admin system, and the dashboard remains. Only the owner's Telegram account can open it; members have their own members' app, apart from it.

Settings and the rest of System stay on the dashboard. The mini app is reached at an https address on the owner's own domain; the rest of the dashboard is never reachable from outside the owner's computer.

It opens from the menu button of the member's own private chat with Nocheh, at its own page on the mini app's address. A member's identity comes from Telegram's signed launch data, accepted only for a short time, with no password. Whether they are an active member is looked up on every call, so removing or pausing a member ends their access at once, and anyone else, a stranger or the owner included, gets no data from it. Its calls go to member routes of their own on Nocheh, never through the dashboard, the owner's routes or anything that acts for the owner.
- In the members' app a member sees one board per project that holds a group they joined: the tasks set on that project itself and the tasks of their own groups in it, never another group's tasks or the owner's personal tasks, and each task only as it is on that board for that project's chats. A group counts only while Telegram has recently confirmed the member in it. With Tasks read and write they add, edit, comment on, finish, reopen, trash and restore tasks there, other people's included, and set reminders to themselves; with read only they read. Each task shows its status and the shared columns by the owner's names for them, and who does it as the project's chats see it ("Sara, Omid and 2 other people"). The members' app is in English only, with no language choice. Their groups show with each one's board, and Settings has where their reminders go, their own pending reminders and Sign out, which signs them out on every phone.

<area name="Operations and acceptance">

- Personal-use readiness is evaluated across the documented Nocheh scenarios in a simulated Telegram environment. Telegram services are mocked from the Bot API documentation without requiring real Telegram traffic for that rehearsal. The evaluation includes Nocheh's product outcomes and the Hermes and Honcho integration, recovery, and audience boundaries. Simulation evidence identifies substituted services and untested model/provider behavior; it does not claim exhaustive proof or replace separate live release gates.
  - The simulated rehearsal is a release gate for the owner's private side. It plants private marks in the owner's private chat, in a plain message, a native note, a personal task, a private job and the owner's default role, and finds each of them again there. Questions with a probe mark in a group, a group's topic and a project's chat then search, recall, list tasks and read job status, and no model request made for any of them holds a private mark. At the end, no private mark is in anything Telegram was sent outside the owner's private chat: a message, an edit, a button, or the answer to someone else's button press. Without the list of planted marks the gate fails. Two groups of one project and a third group in no project each get their own mark: the owner's question in the first group finds only that group's mark and only its tasks, never another group's task title, count or tag; only the owner's own answer in a group of that project carries Answer privately; someone else's tap on Answer privately gets only the only-asker notice and runs nothing; after the owner's tap and `/start`, the private answer holds both project groups' marks and tasks, never the third group's mark or a private mark; and every send it took is recorded. Once the owner turns the project's "Share group chats" on, the same question in the first group finds both project groups' marks and tasks, never the third group's mark or a private mark, and carries no Answer privately. Unit checks cover what the simulation has no fake for: a group turn's Notion result never names a Notion page, and a mini app launch by anyone but the owner, a member included, is refused before anything is read. No answer of the members' app, and no reminder sent to a member's chat, holds a private mark, another member's mark, another group's task, the owner's personal task, a private column, the owner's names for people or a comment from before a task joined the board.
- Backups quiesce ingress before writers and establish one recovery point across archive, derived, and control databases, original files, durable journals/receipts, guarded owner edits, native stores, configuration, and a conservative spending-ledger snapshot. Checksums and table fingerprints verify recovery; rebuildable dependency caches are explicitly excluded.
- Backups run automatically every day at an owner-set time and time zone, and the owner can turn this off. The owner sets how many automatic backups are kept; older automatic backups are removed, and backups the owner starts are never removed. An automatic backup never fills the disk the installation runs on. A link a command left inside a profile's workspace is backed up as a link and restored as one, never followed; special files such as sockets are skipped, and files a command made unreadable inside its workspace are left out and listed. System › Backups warns when free disk space is low.
- The owner can turn on encrypted off-site copies: each new automatic backup is encrypted on the machine with the owner's passphrase and stored in S3-compatible storage the owner chooses, which only ever holds ciphertext. The owner can test that the newest copy opens and checks out, and can recover a backup from a copy on a new machine.
  - Off-site storage is configurable: the owner picks Cloudflare R2, Backblaze B2 or other S3-compatible storage. Cloudflare and Backblaze connect without the owner creating keys or typing storage details by hand: the owner gives one credential made on the provider's own page, and Nocheh sets up and tests the rest. The passphrase stays the owner's own and never leaves the machine in plaintext.
- Backups include Inngest PostgreSQL history and Redis queue/run state at the same quiesced recovery point as Nocheh evidence. Restored workers, schedules, and event publication remain inactive. Backup, restore, and service shutdown execute through containerized management independently of Inngest, with maintenance progress visible in Nocheh.
- Restore uses a separate project and state directory with Telegram disabled, and archive workers, tool execution, scheduling, and Honcho attachment held. Restore does not activate services or reset a newer spending ledger.
- Recovery cutover reconciles snapshot-era pending work with source evidence and shuts down source authorities before activation. Rollback uses the matching code/images and a verified inactive snapshot, never an older runtime against a newer live database.
- Candidate compatibility checks build pinned runtime/native assets in isolation without live state, credentials, or test network. They do not activate candidates or change saved pins. Upgrade acceptance covers capture, guards, audience access, approvals, native memory, restore, and single-authority operation.
- Release acceptance includes real chat through a configured provider, literal detection, provider failure handling, and local Compose recovery. Real Telegram acceptance covers owner replies, selected-group behavior and intentional silence, private/group isolation, voice notes transcribed before their reply with original bytes kept, exact owner approval, and reconnect/restart without duplicate effects.
- Real/live MVP tests have a retained acceptance record and are not all rerun after every change. When an operating installation has no relevant difference from one whose checks passed, those passes are carried forward with the equivalence recorded. Only affected checks whose evidence is invalidated by a relevant change or failure, and remaining unpassed checks, require live verification. A new commit alone does not invalidate a pass.
- Live Telegram acceptance records fresh event IDs and timestamps for an owner retirement of a captured message and a non-owner human reaction change and removal on an old message in a selected group. Missing group admin rights or absent reaction delivery are pending or failed checks, never passes.
- Missing credentials, unrun checks, or healthy containers do not establish acceptance. Provider cutover, Honcho activation, and release have separate gates; Git integration is not activation.
- Validation evidence excludes real conversations and credentials. Measurements distinguish deterministic preservation/enforcement from finite observations of detection, privacy filtering, memory quality, and latency.
