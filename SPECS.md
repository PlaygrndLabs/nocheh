<area name="Nocheh">

- Nocheh is a personal AI brain. Owned source data, useful memory, and reasoning are the product. Telegram is an adapter; Hermes is the first replaceable runtime. Memory is swappable too; Honcho is the current long-term memory.
- Nocheh owns its dashboard, CLI, archive and files, source identities, audience policy, guarding, approvals, and integration lifecycle.
- Nocheh learns from permitted sources, organizes knowledge, prepares changes, and explains its work under clear owner supervision. Projects are optional aids to understanding. The agent manages routine work within explicit owner authority; the owner can inspect results and decide exceptions through ordinary private conversation and the dashboard.
- Dependable answers are more important than speed. Answer dependability is evaluated separately from response time.

<area name="Foundation and deployment">

- Nocheh uses TypeScript services, React, npm for dependency management and project scripts, and thin Python integration with Hermes. Tested upstream revisions and dependency versions are pinned.
- Local Docker Compose is the supported development, unattended operation, and acceptance environment. Each installation has one Compose project containing all services, including the owner dashboard and executor.
- Nocheh provides an exact-revision app deployment script and agent skill for an existing local Docker Compose installation and an existing VPS checkout. A read-only plan identifies the target; an explicit apply verifies checkout ownership and revision, deploys the app service, and checks health. Credentials and runtime state remain in their installation. Deployment is separate from live acceptance and release.
- Agent-facing admin, deployment, and development skills are available from the repository's `.agent/skills` directory so AI agents share the same operating instructions. `.agent/` is the only repository directory for agent support files; there are no `.agents/`, `.codex/`, or `.claude/` directories or `CLAUDE.md` compatibility link. Root `AGENTS.md` defines working instructions.
- `./bin/nocheh` is the single owner-facing command for installation, admin inspection, deployment, archive, security, and security profile operations. Its command flags, output formats, privacy defaults, and data contracts are stable.
- Repository tooling lives in `tools/cli`, `tools/operations`, `tools/runtime`, `tools/acceptance`, `tools/development`, and `tools/build`. The dashboard source lives in `dashboard`; TypeScript services live in `src`; Nocheh's Hermes plugin and Honcho service code live in `services/hermes` and `services/honcho`. The Hermes plugin retains its `plugin.yaml` identity and `plugins/nocheh` profile links. Agent skills live in `.agent/skills/nocheh-admin-cli` and `.agent/skills/nocheh-deploy`.
- Repository checkouts and live source mounts use those canonical paths, with no legacy `integrations/`, `scripts/`, `web/`, or `admin/` directories.
- Repository files and directories have a defined product, tooling, test, acceptance, or documentation role. The tracked tree contains no empty files or directories.
- Git tracks source code, build and deployment configuration, documentation, and explicitly synthetic test fixtures. Runtime state, generated output, live acceptance reports, source content, operational identifiers, credentials, and installation metadata remain in local ignored state outside repository commits and Git history. Tracked acceptance material contains reusable procedures and non-identifying status summaries.
- Database size and other operational storage do not grow uncontrolled in any component. Owned original source data is retained without a bound by design. By owner decision ("keep data for ever"), workflow history and Hermes delivery logs are also kept forever unless the owner sets a retention period.
- The setup has one clean structure: root `docker-compose.yml` defines the three-store installation directly, with no separate storage-layout overlay or selectable legacy runtime. Compose creates owned volumes for a fresh installation.
- Local development uses the root `docker-compose.dev.yml` override with the operating Compose file; isolated test configuration lives under `deploy/acceptance`. The development launcher verifies operating state and service ownership before starting.
- Local development runs the full operating `nocheh` Compose project, including Honcho, in source-watched mode on the normal localhost ports, using the configured Telegram bot, local application data, and the installation's provider keys and credentials. The existing `nocheh-app` service watches mounted source code, compiles changes, and reloads running services live without manually rerunning the app or rebuilding Docker images for ordinary source edits; development adds no builder service. Only one Nocheh Compose stack and one Telegram poller run on a local host at a time. Switching between development and unattended operation preserves the same source data, memory, and bot identity.
- Deployment service names identify their tool and purpose. `nocheh-app` combines the API, source capture, outbox publication, and ordinary Inngest handlers; `nocheh-security` combines the broker and guard outside agent execution. The single managed Hermes core service is named `hermes`; its isolated-agent sandbox launcher is named `hermes-agent-sb`; and Nocheh's PostgreSQL service is named `nocheh-db`. Hermes serves its built native dashboard through its managed web server. The owner dashboard and executor run as separate Docker services, independently of the application and Inngest. The executor service is named `nocheh-executor`. Stores, credential-bearing gateways, and isolated agent launch authority retain separate boundaries.
- The supported Node runtime is 24.x. Ordinary workflow execution has concurrency four, executor workflows two, and separate API/capture and workflow PostgreSQL pools capped at eight connections each. Inngest outages cannot prevent capture, API startup, or management operations while Docker is available.
- Nocheh uses three databases on its PostgreSQL service, with separate credentials and explicit repository interfaces: `nocheh_archive` for original evidence, `nocheh_derived` for guarded versions and generated data, and `nocheh_control` for configuration, audience policy, projects, sharing permissions, approvals, jobs, retries, authorization epochs, and execution receipts. Hermes, Honcho, and Inngest retain their separate native stores. Provider monitoring may retain its own operational SQLite state.
- The PostgreSQL service provisions the archive, derivative, control, and workflow databases before it reports healthy. Nocheh has no standalone `nocheh-store-bootstrap` service. The running application and security services use restricted store roles, never the installation administrator credential.
- Product source data is portable across runtime and memory implementations. A replacement runtime satisfies the same capability, capture, audience, and enforcement contracts.

<area name="Archive and provenance">

- The archive database contains only original observations, messages and edits, source identities, observed relationships, original file manifests, hashes, and capture provenance. Original file bytes live in the owned immutable file store. All guarded versions, transcripts, extractions, generated artifacts, runtime context, and learned interpretations live outside the archive in `nocheh_derived`.
- Files are important: their text is read at capture and import and goes through the secret check, since a file may include credentials. Nocheh calls a ready reader (Hermes's document reader for Word, Excel, PowerPoint, old Office, OpenDocument, RTF, EPUB and PDF) from its own preparation step instead of building its own.
- Photos and image files are read once when they are saved, live or imported, by Hermes's own vision tool with the Images model of Settings › Models (the main model unless the owner picks another). The reading is the image's text and a short description, from an instruction the owner can edit in Settings › Assistant; it goes through the secret check, since a screenshot may show a credential, and the original image is kept. A reply waits for it; a busy provider is tried again, and an image that cannot be read records why. Stickers, animations and video keep their original only. Each reading's tokens and cost show on the Usage page, and an import shows how many images it will read and what that costs before it starts.
- Original audio, video, and files are the source; transcripts and extractions are replaceable, versioned derivatives. Every derivative retains stable typed source references, source revision, input hash, producer/version, and configuration fingerprint. A model output never replaces an original.
- Observed incoming messages and successfully delivered assistant messages are source evidence of what was said. Drafts, prompts, internal contexts, generated shares, schedule definitions/fires, and execution attempts are not source observations and remain outside the archive.
- Every confirmed delivered assistant message appears as an original source record with its observed text in the Messages page's Assistant replies filter, including replies recovered from retained delivery receipts. Conversation filter counts reflect source records shown in Messages rather than operational records.
- Incoming Telegram events enter a durable spool before acknowledgment and commit idempotently before downstream assistant processing. An update that the runtime's Telegram library cannot parse never stops polling: its original is captured whole, polling advances past it, and the count is visible in polling health. Duplicate updates, database outages, restarts, partial downloads, and retries preserve observations and recoverable progress.
- The owner can retire or restore any captured Telegram message, including text, voice, media, edited messages, and confirmed assistant replies, from Messages. A retirement is an owner decision in control storage keyed to the stable message identity, so every observed revision shares it. The action uses a revision check and idempotent operation ID, and its history remains inspectable. Originals, files, transcripts, and delivery evidence stay immutable and available to the owner. Messages labels retirement separately from reply and delivery status; retirement is never labeled as an observed Telegram deletion.
- Message management in Messages makes retirement easy to complete and understand: a reversible retirement takes one explicit action, its saved active or retired state remains visible beside that action, failure appears in place, and restoration is clearly offered as Undo. The interface explains that retirement does not delete the original or recall a Telegram reply already sent. When the owner retires a message, Messages also offers the delivered assistant replies that directly answered it or repeat a substantial verbatim excerpt of it, and the owner can retire the selected replies in the same action. Offered replies remain available unless the owner selects them.
- A retired message and reactions on it are excluded from future agent retrieval and learning. Dependent contexts and inferred conclusions are invalidated before reuse and rebuilt only from remaining permitted evidence. Retirement stops a pending reply and requests cancellation of a running turn before delivery begins. A confirmed sent reply remains confirmed; an uncertain send remains uncertain and is never automatically repeated or labeled cancelled without a cancellation receipt. Restoring a message permits future use without rewriting history. A second message never implicitly retires the first.
- On retirement, Hermes' own stored conversation history replaces a retired message with a placeholder that says it was retired and gives its message ID (its archive source ID); a retired assistant reply is replaced the same way. Restoring a message does not restore it in Hermes' history.
- When asked which message came immediately before the current one, Nocheh does not treat the current question or the latest accessible history item as proof of that order. If the order cannot be verified across messages it may not access, it states that uncertainty without revealing retired content.
- When asked what a retired message contained or was about, Nocheh does not treat the current question or another accessible message as the retired source. If the retired content is unavailable to the agent, it states that it cannot determine the content.
- Capture, attachment retrieval, assistant work, and approved actions have independent progress; slow inference does not block source capture. Unsupported or malformed input is retained with a visible processing outcome.
- Browser text and attachments are captured before command interpretation or inference. Scheduled definitions and fires retain stable operational identities in control storage. Outbound results, execution attempts, and delivery receipts remain separate evidence; confirmed delivered messages can reference that evidence.
- Search, source reads, artifact downloads, graphs, export, and replay preserve identities and enforce audience access. Queries are bounded and paginated. Archive search and the default archive graph show original evidence; source details link to derivatives. Knowledge retrieval can combine authorized sources and memory with clear labels.
- Messages browse pages show the newest received source records first, with a stable order for records received at the same time.
- The owner dashboard presents archive records in a searchable, paginated, responsive table. Its default browse and search results contain all source records only, excluding wire captures, outbound intents/results, generated drafts, and other operational records. Visible filters let the owner narrow those results by message direction, conversation scope, and reply-processing state; source-only filtering is never an invisible fixed choice. The table identifies message type and conversation alongside the message, uses a status column for incoming reply processing and confirmed outgoing delivery, and shows the delivered assistant message beneath the incoming message when a durable causal link is available; that linked message opens its own immutable source record. Incoming messages show reply-processing state separately from capture and guarded-copy readiness. A pre-delivery failure is labeled as retry scheduled, while a genuinely uncertain Telegram delivery is labeled as delivery uncertain and explicitly not auto-retried; neither state is described as an approval. A reply that Telegram definitively rejected is labeled as rejected by Telegram, and a voice note without a transcription provider is labeled as archived without transcription; neither is described as a reply that was not needed. Selecting a row opens a concise message detail view in a side drawer over the table, rather than below the page, led by the immutable original and the revision-checked editable agent copy. Active transcripts are visible in the ordinary message detail and labeled as generated; other generated items, provenance, raw fields, source identity, and export controls remain available under clearly labeled advanced details instead of dominating the ordinary view; immutable original evidence remains visibly read-only and is never edited as a raw database row.
- While the Messages page is open, it receives a live refresh stream and shows new and changed source records, conversation counts, reply state, and selected-message details without a manual reload. Refreshes preserve the active search, filters, selection, and pagination. The view reconnects after interruption and identifies when its live connection is unavailable.
- Messages shows a conversation reply and each associated external action as separate outcomes. When an incoming message has a proposed Telegram action, its row visibly says approval is pending and links to that exact review, including when the conversation reply was already sent. Approval and action execution do not count as confirmed Telegram delivery. The owner can filter incoming messages with pending action approval.
- Message rows and original-message details identify voice and other non-text content by its original content type, including when the message has no text. When text and non-text content coexist, both remain visible. The owner can see attachment readiness, download original files, and explicitly preview supported audio, video, and images without automatically loading them. Missing text is never presented as missing message content.
- Reaction rows in Messages show more detail of reactions: observed additions, changes, removals, and anonymous count updates. Each row shows the reaction emoji or known type, the actor when Telegram supplies one, and the target message ID. Unknown reaction types and incomplete observations remain labeled as unknown or updated without assigning meaning or implying current state.
- A voice message plays from its message detail with one deliberate play action when playback is allowed by the browser. The active transcript is readable alongside the original audio and visibly distinguished as generated text. In Messages browse and search rows, a preview of the first active transcript appears beneath the original message content and before any linked assistant reply, labeled as generated text. When no active transcript exists, the detail says so explicitly and the row retains its original content type without a transcript preview.

<area name="Versioned derivatives and reprocessing">

- The owner can list derivative versions, inspect provenance, reprocess selected sources from original bytes, and activate a prepared version through the dashboard, API, and CLI. Jobs are idempotent and edits use revision checks.
- Reprocessing preserves immutable output versions, original bytes, and owner-edited guarded versions. Guard preparation succeeds before activation. An old owner edit is never silently applied to different generated text.
- Changing the active derivative invalidates dependent contexts and refreshes affected learning. Completed derivative results are durable before workflow completion receipts.

<area name="Imports and portability">

- The database design supports long-term data import across platforms, including future Slack and Discord adapters. Adding a platform preserves existing source data, identities, provenance, and audience boundaries.
- Manual import accepts Telegram Desktop single-chat and multi-chat JSON exports with supplied media, including ZIP input. Preview shows scopes, message counts, dates, and missing files; missing media does not make supplied text unusable.
- Imported history defaults to owner-private scope. Mapping it to an existing group requires explicit owner selection; Desktop identities are not guessed to be Bot API identities.
- Importing group chat history from exported Telegram data is fully compatible and prevents duplicates and similar issues. Identities that Telegram proves are shared: a Desktop sender is the same person or chat the bot sees live, and a supergroup or channel export mapped to that same live chat contains the same messages. A message already captured live keeps its imported copy as evidence, counts as a duplicate, and is neither learned nor retrieved twice; a newer export of a message replaces the older one in memory.
- Import jobs persist progress, duplicates, revisions, errors, cancellation, and resumable identities. Uploads and extraction are bounded and reject escaping paths and symlinks. The supplied export bytes retain import provenance.
- Historical import and replay send no old conversation replies. Importing makes sources searchable; learning requires explicit opt-in at import confirmation, retained across retries.
- Nothing runs at import except storing, preparing (reading files) and the secret check. The secret check runs once at import and is saved, checking many messages of the import in one call. A Telegram Desktop export's messages file (result.json) can be up to 128 MB, and the messages file is not re-sent with every batch.
- The Import page shows each step's progress: saving, reading files, secret check. The import is marked ready when those are done, and the owner gets a Telegram message. Until then, a question about that chat says it's still importing and how far along it is. The page shows the learning cost estimate before the owner presses Start; an estimate is acceptable.
- Source-only exports preserve original observations, files, identities, and capture provenance. Complete portable exports also preserve generated records and guarded history in separately labeled domains. Reimport routes records to their proper stores. Accepting saved guarded copies requires an explicit trusted restore; ordinary imports prepare their own projections and divergent histories are conflicts.
- Portable export also includes registered native profiles' notes, scope markers, and SQLite session snapshots including committed WAL state. Runtime-generated material is labeled separately. Per-file hashes and a completion manifest support verification; operational credentials and configuration are excluded.
- Portable export does not activate an installation or imply one common recovery snapshot. A quiesced backup supplies a common recovery point.
- Portable import retains access settings, requests, grants, and decisions as inspectable history. It does not create active grants or replace the destination's access settings, even when installation generation and authorization revisions match.
- Complete portable export and coordinated backup preserve knowledge proposals, organization delegation history, decisions, and application and undo receipts. Portable import retains saved authority as inactive history. Import and inactive restore cannot enable organization permissions or reactivate queued organization work through restored control records.

<area name="Platform-independent source model">

- Source identity separates platform, source namespace, object kind, and opaque external string ID from connector installations, import jobs, and local audiences. Separate observations may refer to the same source object and revision without losing their distinct originals or provenance. Unproven identity mappings remain separate.
- Common source relationships include authors, containers, threads, replies, reactions, and attachments. Reaction observations preserve the target message, reaction, actor when supplied, source timing, and observed changes, including activity on old messages. Source objects also represent non-message data. Unknown platform fields are preserved; partial, complete, unknown, and observed-deletion states remain distinguishable without inferring missing history or revision order.
- Relational identities and relationships support common queries; versioned metadata retains platform-specific extensions. Supplied original bytes remain separate from normalized projections. Projection metadata does not bypass guarding or audience access.
- Adapters and source projections carry explicit versions. Database migrations preserve existing source references, original evidence, guarded revisions, learning consent, and export/reimport behavior. Source hierarchy and relationship targets do not grant audience access.

<area name="Guarded projections">

- Guarding has two modes: `on` and `off`, with `on` the default. Durable guarded projections are prepared at ingestion for source revisions, including imported and derived text, and reused without repeated detection of the same prepared content. Guard inputs, outputs, revision history, and owner edits live in `nocheh_derived`; guard policy and authorization epochs live in `nocheh_control`. Owner edits are durable data, never disposable caches.
- A trusted model detects literal secret substrings; local code validates literal membership and spans, merges overlaps, and masks them. All other text remains exactly unchanged. Detection quality is measured; it is not a guarantee that every possible secret is found.
- Ordinary phrases and synthetic test markers in voice transcripts remain readable when they are not used as credentials. A credential label or unmistakable credential value remains guarded.
- The owner can inspect originals, file bytes, preparation status, guarded copies, and revision history. Only guarded projections are editable. Saves use revision checks; restoration creates a new revision. Saved owner edits are authoritative and cannot be re-masked or overwritten by background preparation.
- `on` selects only current guarded data for agents, tools, memory, and embeddings, including trusted reasoning routes. `off` selects originals with the same audience and effect checks. Guarding is neither archive encryption nor a switch that disables authorization.
- Preparation persists completed work and retries incomplete work. Unknown, unavailable, stale, or unbound guarded context fails closed without an original-data fallback.
- Every physical model attempt validates current content revisions, audience, and destination, including complete history, native memory, retrieved sources, tool results, auxiliary calls, redirects, retries, and provider changes. Unsupported transports, opaque server-side history, and provider-hosted tools that bypass this boundary are rejected.
- Trusted detection and media preparation receive the original inputs necessary for their task. Raw media reaches only explicitly trusted perception or transcription destinations; resulting text is stored and prepared under the same policy as typed text. Model names alone confer no trust.
- Owner edits and representation changes retire affected contexts, credentials, caches, and Honcho sessions before reuse. Revocation precedes availability of changed guards or access policies; interrupted changes stay unavailable until reconciliation completes. Rebuilding uses current authorized sources; original and guarded Honcho memory does not mix. Retiring local data cannot retract data already delivered externally.

<area name="Memory and audience access">

- The owner's private assistant can recall across all registered native memories and archived sources. Groups and topics use versioned `isolated`, `approved` (default), or explicitly selected `filtered` sharing. Topics inherit group preferences and keep distinct conversation history. By default, all topics of a group share one memory: a turn in a group's General chat or in any of its topics recalls what was said in all of them. The owner can instead keep each topic's memory separate with “Topic memory” in Chats › Sharing or Settings › Telegram; “Whole group” is the default.
- Telegram General-topic handling supports ordinary messages without topic markers in the group's base conversation scope, which shares the group's memory with its named topics unless the owner keeps topic memory separate. Existing captured General messages can resume from their original envelopes without rewriting archive evidence. Incomplete or malformed topic markers remain unresolved and do not broaden access.
- Audience access is enforced in storage, tools, source reads, file access, notes, sessions, graphs, and delivery. Policy changes invalidate stale capabilities and contexts; audience authorization is rechecked before delivery.
- Each physical Telegram send, including response chunks and native retry or formatting fallbacks, preserves the authorized chat and topic and rechecks current authority and cancellation. An unavailable topic never permits delivery in General or another topic. A partially delivered response is not automatically repeated or described as fully cancelled.
- Approved shares expose exact owner-approved content revisions. They do not grant access to private originals or private provenance. Filtered sharing exposes only derived material reviewed for the target audience from explicitly selected sources; failures withhold wider knowledge. Semantic privacy filtering is fallible and separate from provider guarding.
- Live conversations can drive native memory review. Imported-content learning needs explicit approval during import; preparation or attachment does not grant that approval. Background review has no external-action tools and keeps source facts separate from inferences.
- Memories and retrieved content are evidence, never security policy or action approval. Conversation conventions guide interpretation within those boundaries. The security boundary preserves complete authorized native memory, source references, history, model choice, reasoning settings, and configured context limits without introducing lossy summaries or extra context-work approvals.

<area name="Conversation state and conventions">

- The agent automatically learns contextual meanings and traces the state of tasks, commitments, and other subjects from permitted message relationships, reactions, edits, and stated conventions in background learning, even when it does not reply. New activity on an old message can update the agent's understanding. Learning itself sends no acknowledgment or external action.
- A "check" emoji reaction on an old message can mean it is done; this is a contextual interpretation, not a fixed meaning for that emoji. The agent learns how people use reactions and relationships from the conversation and its conventions, preserving uncertainty when the meaning is unclear.
- Explicit interpretation rules can be supplied in the infrastructure system prompt, in each group or project's contribution rules, or stated by any participant in the group. Local rules apply locally; project-wide rules require an unambiguous project reference. Explicit applicable conventions take precedence over inferred defaults. Conflicting explicit conventions stay visible until evidence or an owner correction resolves them.
- Inferred state and conventions live in `nocheh_derived`, retain source activity, applicable scope/rules, uncertainty, producer details, conflicts, and revision history, and remain distinguishable from observed facts. Later activity, corrections, or rule changes can revise them. Original observations remain in the archive and their guarded representations remain in derived storage.
- The owner can inspect what Nocheh learned, filter by scope, follow evidence, inspect history and conflicts, and correct or retire interpretations in the dashboard, API, and CLI. Owner corrections override the affected interpretation and invalidate or rebuild dependent memory contexts before reuse.
- Learned interpretation cards display their details as badges, visibly identify revised entries and the active revision, and align action buttons across cards in each row. The dashboard can filter revised entries. An interpretation's detail view shows the active and original wording together after a revision, keeps the complete revision history accessible, and confirms a saved correction without obscuring the original wording.
- Contextual interpretation uses guarded Honcho reasoning with authorized evidence and applicable conventions. A bounded provenance reader follows conclusion ancestry to ingested source references and explicitly reports unavailable exact citations.
- Reply/reaction context resolves independently of graph pagination. Duplicate, delayed, removed, anonymous aggregate, and unresolved observations remain distinguishable; missing context is not invented and unknown topic membership does not broaden access.
- The Telegram adapter explicitly subscribes to individual and anonymous count reaction updates when Telegram delivers them. Every update remains original evidence. Current individual reaction state is maintained per target and actor, with anonymous counts separate. Changed or removed reactions make superseded observations and inferences unavailable even when no replacement conclusion is produced. Edits and reactions on old messages update learning silently and do not trigger a reply to that old conversation.
- Interpreting a reaction or group convention does not grant action approval or change administrative, provider, privacy, or guard policy. State inference follows the same audience and learning-consent boundaries as other memory.

<area name="Projects and explicit sharing">

- The owner can create, edit, archive, and manage projects spanning multiple chats/topics through the dashboard, API, and CLI. Each chat/topic has one effective project; a topic inherits its group's assignment unless explicitly assigned.
- Project membership grants no cross-chat access. The owner chooses sharing sources, destinations, enabled state, and approved or filtered mode, with preview and revocation. Learned conventions retain their applicable scope and do not silently transfer between projects.

<area name="Agent-led knowledge organization">

- The owner can delegate automatic organization for selected exact conversations, permitted existing projects, and optional creation of new projects. Permissions start disabled, last until revoked by default, and support an optional expiration. Creating a project, assigning a conversation, and changing organization permission never grant participant access, knowledge access, or external-action authority.
- Automatic operations are limited to creating projects and assigning conversations. Evidence-backed discovery may create a project without assigning its source conversation. Mentioning a project alone never reassigns that conversation. Project renaming or archiving, identity linking, corrections, sharing-policy changes, and fact-access changes require exact owner review.
- Permission covers exact conversation scopes. A group assignment that would affect an unselected inheriting topic requires owner review. Review presents the exact inherited topic consequences separately from direct assignments; newly discovered inheriting topics require a fresh proposal and never silently expand the approved effect or delegated scope.
- Each delegation records assignment revisions for its selected conversations. A subsequent owner edit suspends automatic organization for that conversation until the owner explicitly resumes it from the current assignment. Editing the permission's name or other settings does not implicitly resume suspended conversations.
- A delegation records a capture-sequence watermark when its authority starts. Historical reprocessing, imports, and backfill do not acquire automatic organization authority. Owner-private requests may explicitly prepare changes using permitted historical evidence.
- Runtime integrations expose typed knowledge inspection, change proposal, and proposal-status tools. Enforcement and durable state belong to Nocheh and are reusable by replacement runtimes. Owner-private conversations can prepare project changes, entity corrections and link decisions, sharing-rule drafts, and exact fact-access changes through existing validated, revision-checked review operations. Agent processes receive no admin credential or arbitrary owner-API proxy.
- The consented live-learning result can include an optional structured organization proposal without a separate model request for each message. Model output describes a change; trusted code independently checks its authority. Only proposals matching active organization permission apply automatically; other changes enter the owner decision inbox. Automatic filtered sharing uses owner-selected sources and destinations independently of organization permission; exact fact grants and external actions have their own approval rules.
- Proposals are durable before application and retain original evidence, guarded proposal contents, authorization, before and after values, and application receipts. Related project creation and conversation assignments apply in one control-database transaction with one receipt and at most one memory invalidation. Unchanged assignments are no-ops and do not repeatedly rebuild memory.
- Application rechecks delegation and revision, installation generation, guarded evidence and proposal contents, learning consent, source retirement, project state, and assignment revisions. An unrelated epoch change from completed learning is acceptable only after unchanged relevant dependencies are validated against the current binding. Untrusted source content never manufactures authority.
- Deduplication uses original evidence and intended changes, excluding transient learning-job and epoch identities. Repeated learning, retries, and restart reconcile the same operation instead of creating duplicate projects or applying a change twice. Waiting, review required, stale or conflicting, cancelled, failed, applied, and undone outcomes remain distinguishable.
- The owner can cancel a pending proposal and undo applied organization with revision checks. Undo preserves original evidence and receipts and cannot overwrite a later owner change. Permission, execution start, and confirmed application are separate states.

<area name="Honcho and native memory">

- Honcho is the primary long-term memory, with reasoning through the memory part's provider and dedicated capped embeddings. Hermes keeps small native `MEMORY.md` and `USER.md` notes alongside Honcho and retains its native sessions.
- For the MVP, Honcho is used as long-term memory under Hermes. Honcho can also be used directly in the future without Hermes, through Nocheh's memory interface.
- Nocheh's Honcho usage definition follows what Honcho's documentation describes, and each user, project, etc. is defined as an entity. A non-standard Honcho usage pattern with high cost is not used.
- Fresh local installations enable and prepare the Honcho service by default, and Honcho memory is turned on for ordinary turns by default once the service is enabled. No live acceptance test is required before it turns on. The owner can turn it off, and the owner's choice stands across restarts; an explicit installation setting can disable the service. Turning it on does not ingest earlier history unless the owner selects that option.
- Honcho production support and read-only inspection are part of the installed memory integration. No separate Hermes-versus-Honcho comparison runtime or experiment workflow is shipped.
- People and projects are the entity types used for connected memory. Exact platform identities are reused automatically. Different people with the same name remain separate; ambiguous name-based or cross-platform matches remain suggestions until the owner confirms them. Registered projects are reused. Evidence-backed discovery may create a project under explicit bounded organization permission; newly discovered projects outside that permission and uncertain project identities require owner confirmation. This exception grants no authority to link people or merge identities.
- An unambiguous reference to a confirmed project attributes that statement to the referenced project instead of the conversation's default project. It does not reassign the conversation or change access permissions.
- Contextual mentions, participation, responsibility, dependencies, and explicit associations are distinct relationship types. Mentioning one project in another project's conversation establishes only a contextual connection unless stronger evidence establishes another relationship.
- Every entity claim and relationship retains source references, the actual speaker, direct/reported/inferred attribution, uncertainty, revision history, and applicable audience. A reported claim never becomes a direct statement by its subject, and a generated interpretation never becomes independent corroborating evidence.
- Canonical identities, confirmed bindings, and review decisions live in control storage. Extracted claims and relationships live in derived storage. Original evidence remains in the archive. Owner corrections override automatic interpretations: chosen person names, confirmed identity links, corrected fact wording, and retired facts survive later platform or model updates. New messages use the confirmed identity binding. Identity links can be undone, and dependent memory is invalidated and rebuilt.
- An installation uses one Honcho workspace. Each person and confirmed project has a stable, versioned Honcho peer mapping derived from its Nocheh identity, and the assistant is its own peer whose messages Honcho does not observe. A project is both a Honcho peer and a session. Each chat, group, topic, import, and project uses its own Honcho sessions, and each session belongs to exactly one audience. Conversational messages use their actual speaker and persistent conversation sessions. Project and mentioned-person observations use separate typed entity-evidence sessions that identify the subject, speaker, source, and attribution without making the subject appear to have spoken.
- Every assistant turn receives bounded, current, authorized Honcho context automatically. Protected context is rebuilt when Honcho finishes new memory work, and its freshness is checked when a message arrives; it is not refreshed on a timer. Deeper Honcho recall retrieves relevant details missing from that context. Ordinary turns do not require an unconditional Honcho reasoning call. Cached context never crosses audiences or survives revocation, representation changes, or a failed freshness check as usable memory.
- A reply reads Honcho's context for its own conversation session, targeted at the speaker. The owner's private conversation can read the whole workspace. A group or topic turn reads only its own chat, including the sessions of every topic of its group unless the owner keeps topic memory separate, plus facts the owner approved for sharing, never a person's unrestricted Honcho representation. Owner-private evidence is never written into a session shared with a group or topic.
- Reactions, rule changes, and other authorization epochs do not create a new Honcho workspace or re-ingest the archive. A correction deletes only the affected Honcho sessions and the conclusions Honcho derived from them, then writes the still-valid evidence again.
- Recall resolves the requested entity first and expands through relevant authorized relationships in bounded batches with cycle detection and deduplication. It preserves the 20,000-character prepared-context ceiling, reports partial results, and explains included paths such as a contextual mention. Permission is checked before exposing an entity name, relationship, count, path, source, or recalled content; project membership and traversal never grant access.
- Nocheh is the sole Honcho ingestion writer. Source, revision, audience, session, and chunk receipts support reconciliation. An uncertain write is reconciled from evidence; absence of confirmation is not permission to resend blindly.
- Every Honcho reasoning or embedding attempt is bound to a current authorized workspace and prepared representation. Retired workspaces and unbound jobs fail closed. Agent processes do not receive Honcho credentials or a direct route around the Nocheh gateway.
- Attachment and detachment are explicit owner operations. Attachment requires accepted live reasoning, embeddings, ingestion, retrieval, restart, and failure checks. Detachment preserves source data, owner edits, and receipts.
- Reattachment rebuilds previously learned sources in the selected representation. Optional catch-up includes consented sources received while detached; optional history includes older consented sources. Neither option grants learning consent.
- Outages and rebuilds expose limited-memory status while preserving available current context, native notes, and archive search. Honcho memory can be rebuilt from owned sources and receipts.
- The owner can re-run Honcho memory, and can replace Honcho memory with a new one, from the dashboard. Re-running and replacing never bring a retired message back into memory.
- Incremental synchronization reports its progress separately from memory availability. Previously ready memory in the current authorized workspace stays available while new sources are processed; initial builds, replacement workspaces, and actual recall failures report limited memory.
- A Honcho workspace becomes ready only after its Nocheh ingestion receipts and current-workspace derivation work finish without terminal queue errors. The readiness check obtains a workspace-scoped, read-only failure signal without exposing queue payloads or error text. Terminal derivation errors keep that workspace unavailable with an explicit failure status; a processed-with-error task is not successful memory. Previously ready context remains governed by its existing authorization and freshness rules while new work is building.
- Audience-filtered entity search, detail, relationships, evidence, uncertainty, correction history, and partial-result status are available under `/v1/entities`. Owner-only controls confirm or reject project suggestions, confirm or undo person links, and correct claims or relationships through the same revision-checked, idempotent commands used by chat and the dashboard. Ambiguity that affects an owner-private request prompts clarification; other ambiguity is queued quietly for dashboard review. Group conversations cannot confirm identities or change owner policy.
- Owner list pagination is omitted when all results fit on one page. When more pages exist, previous and next actions remain balanced around a clearly identified current page.
- Complete portability, coordinated backup, inactive restore, and reset account for entity identities, decisions, relationships, history, peer mappings, and ingestion receipts. Rebuilds create a new mapping version from owned evidence and retire earlier workspaces without deleting originals, owner corrections, or historical receipts.

<area name="Providers">

- Nocheh's services do not include CPA (CLIProxyAPI) or its admin panel. Model calls go only to providers configured in Settings.
- Nocheh settings has a provider feature that lets the user choose existing providers like GPT, Anthropic, etc., or a custom provider such as a hosted gateway by adding its URL and API key. Every provider is reached through the OpenAI-compatible API, and a custom provider's address uses HTTPS. Provider API keys stay on the server, reach only the services that call that provider, and are never shown again after saving.
- One API key is enough unless the user wants to use a different LLM for each part, for example GPT for Honcho and Anthropic for Hermes. Everything is configurable: the user decides which provider and model each part uses. The parts are replies (Hermes), memory reasoning (Honcho), literal secret detection, and memory embeddings. One default provider and model serves every reasoning part unless a part names its own. Embeddings name their own provider.
- A fresh installation has no provider until the owner adds one in Settings. A part without a provider makes no model call: its work waits with the reason `provider_not_configured`, the dashboard says so, and the work resumes once a provider is saved and applied. No provider or model fallback is used: a part sends its requests only to its chosen provider and model.
- Settings › Models lists the providers, their key status, and each part's provider and model. The model list loads dynamically from the added providers: every model choice, the main model included, is a dropdown of the models an added provider lists, loaded as its address and key are entered, before saving, with a way to try the check again when the provider can't be reached; a saved key is sent only to that provider's saved address. The owner can also type a model name. A provider that a part uses cannot be removed. Applying a change restarts the services whose provider or model changed, including Honcho. Every reviewed embedding model stays selectable. Once Honcho memory holds vectors from one embedding model, choosing another asks the owner to confirm a memory rebuild first; applying the confirmed change switches Honcho to the new model and replaces long-term memory from the archive, and an unconfirmed change is refused.
- Each provider has at most one credential, with no provider/model fallback, quota switching, or additional proxy request retries.
- Every voice note, audio file and round video is transcribed, whether it arrives live, comes from an import, or was saved before transcription was set up. Nocheh calls a ready transcriber (Hermes's own, which converts, trims and splits recordings) with the provider and model chosen under Voice notes in Settings › Models; OpenAI with the existing key is the default, an exception to the Anthropic-only rule for transcription. The transcript goes through the secret check like typed text, and the original audio is kept. A reply waits for its voice note's transcript; a busy or unreachable provider is tried again, and a recording that cannot be transcribed records why and never holds a reply. Without a provider key a voice note is archived only, records that transcription is not available, and is transcribed a few at a time once a key is added. Each transcription's audio length and cost show on the Usage page, and an import shows what transcribing its voice notes costs before it starts.
- Honcho has separate budgets for paid embeddings and memory reasoning. Paid embeddings have a $5 total pilot cap, followed by an owner-configurable cap per UTC calendar month starting at $5. The Honcho dashboard lets the owner change that embedding cap from $0 to $15 in cent increments after accepted attachment; $0 pauses new paid embeddings. Honcho reasoning uses the memory part's provider, consumes no embedding dollar cap, and has its own 1,500-request safety bound per budget window. Embedding requests do not consume the reasoning request bound.
- A durable embedding admission ledger reserves the configured model's upper-bound hold before each bounded API request: $0.01 for `text-embedding-3-small` or $0.02 for `text-embedding-3-large`. Successful calls with valid reported token usage settle against the cap at the model's token-priced amount, rounded upward to a microdollar. A definite upstream HTTP error releases its admission hold from the cap; transport failures without a confirmed response, unfinished calls, and successful calls without reported usage retain their conservative hold. Historical monthly failed calls whose response type was not recorded remain explicitly labeled unverified and visible in the ledger, but their holds do not count as confirmed spending or block the monthly cap. The exhausted pilot's historical holds remain counted. The ledger reports original and released holds separately and never represents its estimate as a provider invoice. Settling existing successful monthly calls preserves the exhausted pilot's historical accounting. The ledger cannot reset through restart, restore, a cap change, or repeated monthly activation. Lowering the cap below existing accounting blocks new paid embeddings without erasing existing entries.
- After a paid embedding request fails with an upstream 5xx or transport error, Honcho's egress blocks new paid admissions for a durable, shared cooldown of at least 60 seconds, doubling after consecutive failures up to one hour. Calls during cooldown receive a transient response with a numeric retry delay and create no new spending reservation. A successful request admitted after the latest failure clears the cooldown; an older in-flight success cannot clear it. Memory reasoning remains independent. Failed requests retain their original admission records; only failures with uncertain delivery retain a hold against the cap.
- The Honcho dashboard presents distinct embedding dollar-budget and reasoning request-limit sections. The embedding section shows the adjustable monthly limit, amount counted toward the cap, remaining admission headroom, embedding requests, reported tokens, and an estimated embedding cost. It identifies the estimate as distinct from the provider invoice and makes missing usage reports visible. The reasoning section shows reasoning requests and remaining request allowance without implying API dollar charges. Only an authenticated owner can change the embedding cap, with revision-checked, retry-safe updates.
- When exhausted pilot reservations block Honcho's required live acceptance, an explicit owner command can activate the $5 UTC-monthly cap while memory is detached and unverified. That spending transition does not verify or attach memory, permit historical ingestion, or bypass the live acceptance gate.
- The embedding provider and model are explicit configuration: OpenAI by default, or another OpenAI-compatible provider from Settings that serves the same reviewed embedding models. The default model is `text-embedding-3-small` with 1536 dimensions; selecting `text-embedding-3-large` also uses 1536 dimensions. Vectors from incompatible models are not silently mixed; model changes require rebuilding affected memory. The paid key is confined to the metered boundary.

<area name="Runtime integration">

A failure before Telegram delivery begins remains retryable under a fresh attempt identity; an interruption after delivery may have begun remains an uncertain terminal effect and is never automatically resent. One slow or failed turn does not silently discard a later captured message.

Messages in one private chat, one group's General chat, or one topic keep their order. The reply limit (chats answered at once, three by default) and process parallelism (isolated agent runs at once, shared by replies, memory reviews, browser turns and schedules, four by default) are configurable from Nocheh settings. The reply limit never exceeds process parallelism. Secret-guard checks of different messages also run in parallel; how many run at once (three by default) is configurable from Nocheh settings, and one message is never checked twice at the same time. - In ordinary Bot API chats, Nocheh does not claim automatic detection of message deletions. Telegram Business deletion updates apply only to connected business accounts; ordinary message deletion requires the owner's retirement action in Messages. Reaction delivery in groups requires Telegram admin rights and explicit update subscription, and anonymous counts may arrive late. Nocheh covers its owner DM and selected groups without an MTProto connection.
- When the agent is working, Telegram shows the bot's typing status in the chat or topic it is answering, renewed every few seconds so it stays visible until the reply is sent or the turn fails. It appears only for a turn that will actually write a reply: never for someone Nocheh does not serve, a group message that did not address it, or a fixed reply that needs no model. The status passes the same audience and permission checks as the reply, is not recorded as a delivery, and the owner can turn it off in Settings › Telegram.
- Telegram replies express source attribution in ordinary language and do not show raw internal `nocheh:event:` identifiers. A group reply cannot disclose private source content or private source identity through a citation.
- A complete durable runtime journal with assistant progress and no delivery-stage event may reconcile a legacy interrupted Telegram receipt from uncertain to retryable. Missing, incomplete, malformed, or delivery-stage evidence never authorizes an automatic resend.
- Background native memory review waits for a short quiet interval after foreground activity so immediate follow-up messages can use the profile. Waiting does not consume an execution attempt or replace existing review receipts.
- Nocheh keeps a chat's history when its memory updates, including a new guard epoch from hiding, restoring, correcting or automatically learning memory: the chat continues with its recent messages and delivered answers, and hidden messages stay out. Earlier copies of the chat's history are removed once they have been unused for 15 minutes, so hidden content does not stay behind in them.
- Browser input defaults to owner-private scope; explicit group selection remains group-scoped through capture, tools, sessions, and memory. Reconnect and resume reuse stable stored identities and profile-bound sessions without duplicate submission.
- Durable claims, leases, heartbeats, and result receipts distinguish completion, interruption, and late evidence. Lost responses are reconciled; abandoned work is not automatically rerun as a new external effect.
- Runtime operations provide asynchronous `run.start`, `run.events`, `run.resume`, and `run.cancel` for Telegram, browser, and scheduled channels. Resume reconciles the same execution identity and preserves browser streaming, reconnect, cancellation, and session identities.
- In group chats, Nocheh does not answer every single question that comes up. A question might be directed at the entire group or a specific individual, so Nocheh responds only when personally addressed: a reply to one of its messages, a mention of its @username or a tap on its name, or its name at the start of the message. Its name is its Telegram display name or any name in the owner's “Names that address Nocheh” list. That list starts as “Nocheh” and “نوچه”, and the owner can change, add, or remove names. Every group message is still captured whether or not it addresses Nocheh. When Nocheh replies in a group, it knows what was just said there: the reply sees the group messages since its last turn in that conversation, including messages that did not address it, with who wrote each one and when. The owner can instead let Nocheh answer every message from a permitted participant; “Group replies” and “Names that address Nocheh” appear inside the Telegram section of Settings, and only when addressed is the default. Intentional silence is a valid captured outcome. Group participants cannot approve actions or change administrative, provider, privacy, or guard settings.
- An assistant answer succeeds only after confirmed native completion with a nonempty text answer or an explicit intentional-silence result. Missing, blank, malformed, failed, or interrupted model answers cannot be recorded as successful silence or replaced by a memory-status notice. Pre-delivery failures remain recoverable under the existing receipt and retry rules.
- In each selected Telegram group, only the owner may address Nocheh by default. The owner can fully manage who else may address it through explicit participant grants and denies for that group, including revoking a grant. A deny takes precedence over a grant. Only permitted participants can start a bot response or tool-using turn, and permission is rechecked before delivery. Nocheh acts otherwise only for users added to the allow list: if a user is not allowed, Nocheh rejects and avoids the request with a fixed message in the chat when that user addresses it, without starting a turn or using a model. The owner can edit that message in Settings with the other built-in texts. The owner can inspect and change these permissions in the dashboard and CLI; group participants cannot administer them.
- Hackers can't inject a prompt or a file into the system. Someone Nocheh does not serve is anyone who writes to it in a private chat other than the owner, and anyone in a group or channel the owner has not selected. Their messages are kept as received for the owner to see in the dashboard, but their files are never downloaded, no model checks or reads what they sent, nothing is learned from it, and the assistant never sees it, including in the owner's own search and conversation lists, where chats they named stay out. When the owner starts Nocheh from another Telegram account, it does not receive or act on those messages and cannot see a menu: nobody sees a Telegram command menu for Nocheh. Anyone but the owner who writes to Nocheh privately gets one fixed message, at most once a day per person, without starting a turn or using a model; the owner can edit it in Settings with the other built-in texts. The dashboard marks such messages as not allowed.

<area name="Security and controlled tools">

- A runtime-independent external security service owns the versioned policy and broker contract. Only trusted infrastructure holds provider credentials and provisions isolated turns. Agent containers receive one profile and scoped broker/archive capabilities, not refresh stores, master service credentials, Docker access, or unrestricted egress.
- The trusted dashboard and executor containers have Docker-socket access for backups, restarts, monitoring, and approved isolated tools. This administration authority is outside agent isolation; agents and tool sandboxes receive no Docker socket.
- Explicit denies and mandatory boundaries take precedence over approvals and grants. Policy configuration, previews, and grants are owner-controlled with optimistic revisions; agent-supplied claims have no authority. Routine authorized context work needs no confirmation, and successful routine activity is quiet by default.

An owner freedom setting covers every external effect, Telegram messages and shell, browser and MCP tools alike, at two levels: approval required, the default, and owner requests execute. At the second level an action the owner requests in their own live private conversation is approved by that request. In the private chat Nocheh has access to all of the owner's memory, so by default the owner approves whatever it finally sends; the second level is the optional setting to do it without approval. If a user is allowed and has access to Nocheh, in the same group they no longer need approval and can work freely, because the memory is limited to the group and there is no security problem: a Telegram message that the owner or a permitted participant asks for in a group, for that same group, is approved by the request and posted without a separate announcement. When the owner keeps each topic's memory separate, the same group means the same topic, and a message from one topic to another of the same group behaves like one from one group to another. From one group to another group, the message that is going to the other group is shown and approval is obtained, because group A's message was made from group A's memory and is going to group B. For a message from group A to group B by an allowed member, the allowed member can approve: approval is used just to let the sender see what will be sent, because the memory of both groups is private. That member's card appears under the request in group A, and only that member or the owner can press it. The owner's own requests for another group, and requests for a group where the person asking is not allowed, are approved by the owner in the private chat. When the owner asks Nocheh in a group to send the owner a private message, no approval is needed, because the owner's private chat already sees everything. Only the owner or an allowed member can use Nocheh. There can be one or several projects with one or several groups, where a user can be in all or some of the groups and have access in all or some of them; projects grant no access of their own. A group conversation can list the groups where the person asking is allowed, with their names and IDs. Other requests from groups, including shell, browser and MCP tools and messages to other chats, and requests from schedules and background work still require approval, and deny rules still apply. Each such decision records the setting revision that authorized it. The owner changes the level in Nocheh settings with a revision check; the change applies immediately and revokes no context. No auto-trading is permitted.
- The owner can request a separate Telegram message in ordinary language without naming an internal tool. Nocheh recognizes the requested destination and exact text, proposes the action for owner review, and waits for approval before sending it unless the owner freedom level lets the owner's own private request approve it. A destination includes its concrete topic; “current” refers to the authenticated conversation and topic. Approval of a topic never authorizes a fallback to General.
- Shell, browser, and MCP proposals bind immutable arguments, source event, profile, and scope. Dashboard decisions, owner-private Telegram commands, and Telegram approval buttons use the same approval records. Revocation and authority are rechecked before execution starts.
- The owner is able to approve in chat: a request that needs the owner's approval shows Approve and Reject buttons under the message, and the owner just presses one. The message with the buttons goes to the owner's private chat, including for a request made in a group; Nocheh says things about such a request to the owner in the private chat, and the group gets only a short note that the owner was asked, without the draft. Only the owner's press decides; anyone else's press changes nothing. Later in the same chat Nocheh can look up the requests made there and their current state; a rejected request is finished, so asking again makes a new request, and Nocheh never says a request is waiting or sent without checking. The message shows where the request was made and the exact text and destination, or the exact operation, and after a decision it shows the outcome and no longer has buttons; once an approved message is sent, it says so. When the message with the buttons is in the chat where the request was made, it is the reply to the request and the whole answer; Nocheh sends no separate message about it. It names the group it goes to as a link to that group in Telegram and, in a group with topics, the topic, also linked, by the names Nocheh has seen in that chat. The approval message has a clear, improved style and uses a template: its layout, button labels, outcomes and notices are owner-editable templates in Settings, and the exact message or operation is always shown.
- Controlled shell work runs outside the credentialed agent in disposable containers with only the scoped workspace, no network, credentials, or Docker socket, a read-only root, and bounded resources. The host does not interpret agent-supplied shell commands itself.
- Remote tool operations use approved public HTTPS destinations, pinned DNS resolution, no redirects or ambient credentials, and bounded responses. Browser inspection renders approved content offline; scripts and secondary requests cannot expand permission. MCP supports bounded HTTP JSON-RPC calls without local sampling, roots, elicitation, arbitrary local processes, or interactive authentication.
- Decision and effect records distinguish proposal, authorization, execution start, and observed result. An allow decision is not a receipt. Logs retain safe identities, revisions, and reasons without prompts, credentials, raw URLs, or memory contents.
- An approved Telegram action that the runtime explicitly refuses before recording any send intent, for example while Telegram is disconnected, was not attempted. It returns to the approved queue and is retried automatically while its approval and authority remain current. Timeouts, lost responses, and missing runtime records remain uncertain.
- Uncertain effects are not automatically repeated. Revocation cannot undo an already transmitted effect. Security-service failure or replacement cannot open an unguarded fallback; activation requires acceptance of both isolation and memory/quality preservation. The trusted launcher and host are outside the agent isolation guarantee.

<area name="Scheduling">

- Hermes owns native profile schedule definitions, parsing, editing, cadence calculation, revision checks, occurrence accounting, and session history. Inngest durable waits coordinate scheduled occurrences under Nocheh's single execution authority. Definitions and each scheduled or explicit manual fire are captured before managed execution, with stable identities and separate generated results.
- Schedule configuration shares global/profile/job preference inheritance. Profile locks prevent overlapping browser, Telegram, and scheduled turns. Scheduled tools obey the same approvals and executor settings as other turns.
- Results default to local storage. Selecting Telegram produces an exact approval proposal for each completed result in that job's selected scope. Empty, cancelled, interrupted, overlong, or stale-audience results are not implicit deliveries.
- Owner-private and selected-group schedules support native schedule fields, conflict revisions, cancellation, run limits, and explicit catch-up. Topic schedules and interactive/script/skill jobs are outside the supported capability.
- Occurrences more than 60 seconds late are recorded as missed, including skipped ranges. Catch-up is explicit, never automatic; overlapping slots are skipped. Observed slots and missed ranges consume repeats, manual/catch-up runs do not, and intervals retain their original cadence after downtime.
- Pause prevents future starts; cancellation requests interruption without undoing completed effects. Crashes reconcile stored receipts without repeating uncertain execution. Restored schedulers are inactive.

<area name="Workflow orchestration">

- All product workflows use local Inngest: Telegram attachment retrieval, guarded preparation and dispatch; confirmed imports; native memory review and Honcho synchronization, rebuilding and reconciliation; browser turns; scheduled occurrences; organization; and approved actions. Synchronous security checks and the native agent's internal reasoning loop retain their own boundaries.

TypeScript Connect workers have distinct application and executor identities and versions; Python adapters remain thin. Inngest Cloud is outside this Compose workflow architecture.
- `nocheh-app` initializes the dedicated Inngest database and role before becoming healthy. Initialization preserves existing data and runs safely on repeated startup; no separate database initialization service is required. Inngest starts after the application and Redis are healthy, while application startup remains independent of Inngest availability.
- Fresh installations use isolated Hermes execution, the shared provider route, and evidence-based memory context; saved provider credentials and accepted cutovers retain their boundaries.
- Inngest is the only Nocheh workflow execution engine. Preparation is an explicit prerequisite; Telegram, browser, and scheduled runs consume stored preparation results. Legacy runners and engine-switch controls are absent. Synchronous security and native tool internals retain their own execution boundaries.
- Source capture and relevant state changes have a durable, recoverable handoff to workflow requests outside the archive database. A crash between source persistence and workflow scheduling cannot lose required work or duplicate an external effect. A supervised publisher retries delivery independently of Inngest. Source capture and spool draining continue during orchestration outages.
- Inngest events, step outputs, errors, and logs contain only opaque IDs, versions, counts, timestamps, and allowlisted status codes. Messages, transcripts, prompts, results, tool arguments, and credentials stay in protected stores and are resolved inside executing steps.
- Nocheh owns the workflow registry linking source/job IDs, workflow versions, Inngest runs, attempts, and receipts. Permanent deduplication does not depend on Inngest's finite event-deduplication window. Each workflow family has one fenced execution authority.
- The organization workflow defers owner-turn proposals until confirmed turn completion and enqueues live-learning proposals after learning completes, including completion recovery. Automatic application uses the foreground-reply publication check and waits while replies are active. Owner revocations retain their immediate enforcement path; organization does not disrupt a foreground reply by invalidating its memory mid-turn.
- Retention of Inngest's run history and telemetry (events, run and finish records, event batches, spans, history, traces, trace runs, and disconnected worker connections) is configurable and adjustable in days. By default (`0`) Nocheh keeps those records forever. When the owner sets a number of days, records of runs with no activity for longer than that are removed automatically; an event is kept while a run it triggered is kept. The same setting removes Nocheh's workflow publication records and Inngest run links of superseded dispatches and of workflows closed for longer than that, broker model-call security events and guard invalidation notes older than that, and superseded Honcho context summaries that no current memory generation serves. Security events of actions and tools remain the owner's audit and are not removed by this setting. Retention checks run daily, when the database starts and then once a day. Retention never removes Nocheh's receipts, workflow registry, or Inngest queue state.

The owner can set a number of days from Nocheh settings, after which finished logs are deleted. A delivery or run that has not finished, and a run result not yet handed to Nocheh, is never deleted.
- Inngest owns retry timing. Prerequisite waits are distinct from failed attempts; profile locks and bounded concurrency apply. Current audience, guarded revisions, import consent, and permissions are checked before execution. Terminal, cancelled, denied, suppressed, and ambiguous outcomes cannot automatically restart. Lost responses and uncertain effects require receipt reconciliation, never blind replacement execution.
- Telegram processing and delivery form one receipt-protected native runtime operation with separately visible assistant and delivery progress. Stored transcripts and guarded revisions are reusable. Intentional silence is a valid outcome; uncertain sends stop for reconciliation.
- Confirmed imports use bounded checkpointed batches, preserve upload validation, mapping, identities, progress, cancellation, and explicit learning consent across retries, and send no historical replies. Source preparation, owner edits, consent, and memory generation changes request the appropriate follow-up work. Honcho execution requires its existing attachment and acceptance gates.
- Workflow list/detail and validated retry/cancel operations are available at `/api/nocheh/workflows` and through the CLI, preserving existing job IDs, browser protocols, and compatibility routes. Nocheh shows family/status filters, stage, attempts, next retry, waiting reason, timestamps, source links, outbox backlog, oldest waiting work, connectivity, and stale observations with accessible status text and ten-second refresh.
- Nocheh Monitoring opens with a compact operational summary: running, waiting, failed, last recorded success, and backlog, with expandable details and an obvious link to the workflow scheduler's own console. Summary totals cover all workflow families independently of history filters and pagination. Unavailable or stale observations and uncertain outcomes stay visible in the compact view.
- The Monitoring summary breaks waiting into queued and condition-bound work, shows the leading waiting reasons and workflow families with the oldest waiting record, and explains that one source can produce several workflow records. Denied or rejected closed outcomes are distinct from failures and uncertain effects.
- The detailed Inngest UI is inspection-only behind the Nocheh owner session; execution controls use Nocheh authorization. Monitoring distinguishes retryable and terminal failure, waiting, intentional skip, cancellation, and uncertain effect. Nocheh sends no workflow notifications outside the owner's own Telegram private chat.

A call stopped at its time limit counts as failed too. Each notice goes to the owner's private Telegram chat as one message listing what is new or worse, and System › Health lists the same problems. The owner sets how many automatic backups are kept; older automatic backups are removed, and backups the owner starts are never removed. An automatic backup never fills the disk the installation runs on.
- Backups include Inngest PostgreSQL history and Redis queue/run state at the same quiesced recovery point as Nocheh evidence. Restored workers, schedules, and event publication remain inactive. Backup, restore, and service shutdown execute through containerized management independently of Inngest, with maintenance progress visible in Nocheh.
- Restore uses a separate project and state directory with Telegram disabled, and archive workers, tool execution, scheduling, and Honcho attachment held. Restore does not activate services or reset a newer spending ledger.

Upgrade acceptance covers capture, guards, audience access, approvals, native memory, restore, and single-authority operation.

When an operating installation has no relevant difference from one whose checks passed, those passes are carried forward with the equivalence recorded. Only affected checks whose evidence is invalidated by a relevant change or failure, and remaining unpassed checks, require live verification. A new commit alone does not invalidate a pass.
