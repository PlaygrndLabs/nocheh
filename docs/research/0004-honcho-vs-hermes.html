Nocheh vs Honcho vs Hermes Agent

Whether either of these solves the memory problem better than Nocheh does, and whether Nocheh should become a client, a plugin, a wrapper, or stay exactly what it is. Grounded in Nocheh's actual code (13,553 lines across src/, 41 test files, 12 ADRs) and in both vendors' own documentation.

The verdict, first

Three answers to three questions

1. Which is better? — Wrong comparison. Honcho is a memory service. Hermes is a harness that calls Honcho for memory. So for the memory question, Honcho wins by default: it is the thing Hermes uses when Hermes wants memory. Hermes's own memory is MEMORY.md / USER.md files plus SQLite FTS5 — strictly weaker than what you already built.

2. Is it better to use them in your app? — Honcho: yes, partially, self-hosted, and behind a new port. It genuinely beats your recall layer, and your recall layer is the weakest, least-verified part of Nocheh by your own admission in TASK.md. It does not replace your graph, your tasks, your approval lifecycle, or your audit trail — nor does it claim to. Hermes: no. Not as a dependency, not as a host.

3. Plugin or wrapper? — Neither. Adapter. Nocheh stays the composition root (src/dev-server.ts) and owns the pipeline order. Honcho becomes one more adapter behind one more port, exactly like NVIDIA and Gemini are today. Becoming a Hermes plugin would hand away the one thing you cannot give away: control over what happens before the model sees the text.

Honcho — adopt as component
7.5/10 fit

Strong on the exact axis you are weak on. Wrong shape for your graph. Self-host to keep rule 2 intact.

Hermes — as a dependency
2/10 fit

Python monolith that owns the loop. Structurally incompatible with redact-before-anything. Different product shape.

Hermes — as a reference
8/10 value

MIT-licensed, 25+ channel adapters, cron design, document extraction. Read it, copy the ideas, import none of it.

You framed these as two alternatives that "solve the memory part better." They sit at different layers, and one contains the other:

Honcho — what it is, precisely

Memory as reasoning, not memory as storage. By Plastic Labs. AGPL-3.0 core, hosted platform, self-hostable. Python server + worker, PostgreSQL with pgvector, Redis. TypeScript and Python SDKs.

Data model

Workspace ──has──> Peers      (any entity: you, an agent, an NPC, a client)
     │
     └───has──> Sessions ──has──> Messages
                    ▲
                    └── Peers ⟷ Sessions is many-to-many

Scopes = named sets of Sessions that bound recall visibility

How it processes

  1. Write (synchronous, fast). Message stored in Postgres, reasoning task enqueued, request returns. Nothing waits on an LLM. Up to 100 messages per batch call.
  2. Deriver (async, per-message). Extracts explicit premises then deductive conclusions — formal logic, custom models (Neuromancer / Neuromancer XR).
  3. Summarizer (async). Short summaries every ~20 messages, long every ~60.
  4. Dreamer (periodic). Revisits stored conclusions: consolidates redundant ones, drops stale ones, draws inductive conclusions across patterns, resolves contradictions, updates peer cards. This is the part that has no analogue in Nocheh.
  5. Read — context(). ~200ms, unlimited, free. Returns summary + messages, optionally the peer representation, peer card, and semantically searched conclusions, all inside a token budget you set.
  6. Read — chat(). Spawns a Dialectic agent that searches conclusions, pulls supporting messages, traces conclusions back to premises, and synthesizes an answer. Five priced reasoning tiers. Supports Zod/Pydantic response_format for typed JSON.

Artifacts it produces

explicit premises deductive conclusions inductive conclusions abductive conclusions short + long summaries peer cards directional representations

Note what is not in that list: typed nodes, typed relations, tasks, deadlines, statuses, approval states. Conclusions are prose with provenance, indexed in vectors — not rows in a schema you defined.

Hermes Agent — what it is, precisely

An agent harness, MIT-licensed, by Nous Research. Python. Desktop app for macOS/Windows/Linux plus CLI, TUI, gateway, ACP, batch runner, API server. ~25,000 tests across ~1,250 files. This is a mature, large, well-engineered piece of software — and it is a competitor to Nocheh's harness role, not a component for it.

What it has that you don't

  • 70+ tools / ~28 toolsets — web search, browser automation, vision, TTS, image gen
  • 7 terminal backends — local, Docker, SSH, Daytona, Modal, Singularity, Vercel Sandbox
  • Cron as first-class agent tasks, not shell tasks, delivering to any platform

  • Context compression with pluggable engines and Anthropic prefix caching
  • Skills system, plugins from three discovery sources, LSP diagnostics

What it lacks that you need

  • No typed knowledge graph. Built-in memory is MEMORY.md / USER.md files plus FTS5 session search.
  • No structured memory records. No Decision, Deadline, Blocker as entities.
  • No approval lifecycle. It has dangerous-command detection and approval callbacks for tools, not a pending/accepted/converted state machine for suggestions.
  • No redaction gate. Nothing resembling your secret guard, fail-closed policy, or quarantine.
  • No per-step audit trail of the kind /api/audit exposes.
  • No encrypted-at-rest payload columns.
  • It answers; it doesn't ingest. It is a conversational agent with tools. Your product is a background pipeline that reads and structures a life.

The honest summary of Hermes's memory

Hermes's memory story is "install Honcho." Their own docs compare built-in vs Honcho and Honcho wins every row except file-based persistence and FTS5 search. If you adopt Hermes for memory, you are adopting Honcho with a large Python agent wrapped around it — and throwing away the graph, the guard, the audit trail, and the approval model to get there.

What Honcho genuinely wins — six things

1. Recall quality you have not been able to tune

Your hybrid scorer multiplies (similarity + 0.25·lexical)/1.25 by record confidence, after rescaling cosine from a 0.3 floor. TASK.md says both constants are guesses, and ADR-0012 wired recall into every window — so a bad floor now degrades every analysis, not nothing. Honcho ships a tuned retrieval stack with published benchmarks. Buying a solved parameter-search is a legitimate reason to buy.

2. Multilingual recall — a concrete bug you already documented

src/infrastructure/memory/lexical-score.ts:19 splits on /[^a-z0-9]+/. Your own comment on line 8 says it: "non-Latin text tokenises to nothing… the reason lexical scoring alone was never enough for a multilingual owner." So for Persian input, 25% of your blended score is structurally zero and you are running on embeddings alone — embeddings whose floor is a guess. Honcho's retrieval is language-agnostic by construction.

3. Consolidation you have no mechanism for

You have superseded as a status and applyStatusUpdates() to set it — but only when a model happens to emit a status update for a window. Nothing sweeps the whole graph looking for contradictions, redundancy, or stale conclusions. Honcho's Dreamer does exactly that on a schedule: consolidation, conflict resolution, conclusion weighting, induction across patterns. Over a year of daily Telegram traffic, this is the difference between memory that gets richer and memory that just gets bigger.

4. Latency, at the architectural level

Your write path is: buffer → flush sweep → 189–240s analysis. Worst-case delay before a due batch is analysed is FLUSH_SWEEP_INTERVAL_SECONDS plus four minutes of model time. Honcho's write returns immediately and its context() read is ~200ms. If you ever want Nocheh to answer you — not just file things away — you need a sub-second read path, and you don't have one.

5. Inference beyond extraction

Your contract asks a model to extract what is in a window. Honcho additionally induces across windows ("frequently mentions deadlines, rarely hobbies → time-constrained") and abduces simplest explanations. For coaching, routines, and idea generation — four of your stated domains — that inferential layer is the actual value, and your pipeline has no step that produces it.

6. It gives you the raw-message store you said you wanted

You described your ideal flow as "importer (store all pure data in db)." Honcho is precisely that: messages stored verbatim in Postgres, permanently, with reasoning layered on top. It resolves the tension between wanting the raw log and rule 1 forbidding raw chat as long-term memory — if and only if it is self-hosted and post-redaction. See the design conflict.

The design conflict, stated in their words

This is the single most important paragraph in this document. From honcho.dev/docs/v3/documentation/core-concepts/reasoning:

"Traditional RAG systems treat memory as static storage… Other solutions take an opinion for you on what's important to store, whether through structured facts in databases or predefined knowledge graphs. Honcho takes a different approach: we extract all latent information by reasoning about everything, so it's there when you need it. Our job is to produce the most robust reasoning possible — it's your job as a developer to decide what's relevant for your use case."

Read that as a boundary, not a criticism. Honcho is describing Nocheh in the phrase "predefined knowledge graphs," and it is declining to build one. It also tells you exactly what the division of labour should be:

Honcho reasons. You decide what's relevant.
Honcho produces conclusions. Nocheh's contract decides which of them become a Decision, which become a PERSON_OWNS_TASK edge, which become a pending suggestion awaiting your approval, and which get thrown away. That is not overlap. That is a clean interface between two layers.

The second conflict: rule 2 vs a hosted service

Rule 2 says redact before "buffering, analysis, persistence, logs, context building, or external sync." A Honcho write is external sync. Two consequences:

  • Ordering is already correct. Your guard runs at process-incoming-message.ts:233, before grounding and analysis. A Honcho write placed after that inherits the guarantee for free. Do not write to Honcho from LiveMessageBufferService.execute() — only pattern rules have run there.
  • Hosted vs self-hosted is a rule-2 decision, not a cost decision. Honcho cloud means your entire life corpus — startups, clients, coaching, finances, crypto theses — lives on a third party's Postgres, in plaintext, permanently. The guard removes credentials; it does not remove the fact that you are shipping the corpus. Self-host.

On AGPL-3.0: running an unmodified Honcho as a separate process and calling it over HTTP is aggregation, not derivation. Nocheh's own licence is unaffected. The copyleft bites only if you modify Honcho's source and expose that modified version over a network. Keep your changes to zero and this is a non-issue; write your logic in your adapter, not in their repo.

Read the diagram again — notice what changed

Two insertion points. Both additive. Neither destructive. A write at ⑧ and a read at ⑥. Your pipeline order, your gate, your contract, your graph, your audit trail, all untouched. If Honcho is down, ⑥ falls back to HybridMemoryRetrievalService and ⑧ is skipped — exactly the failure posture ADR-0012 already established for recall ("a recall failure is not fatal, unlike the secret guard").

Where the seam actually is — and where it isn't

The obvious move is to write a Honcho adapter for MemoryRetrievalPort. That is wrong, and it is worth being precise about why.

src/application/ports/memory-retrieval.ts

export interface MemorySearchResult {
  readonly record: MemoryRecord;   ⟵ a typed record: type, source, confidence,
  readonly score: number;         project?, decision?, deadline?, blocker?…
}

Honcho does not return MemoryRecords. It returns prose conclusions, a peer representation, a peer card, and summaries. Forcing that through MemoryRetrievalPort would mean fabricating fake MemoryRecords with invented types and ids — polluting your domain with objects that have no row in memory_records and no place in the graph. That is the kind of shortcut that quietly destroys an architecture.

The right seam: a new, narrow port

src/application/ports/peer-representation.ts

export interface RepresentationQuery {
  readonly conversationId: string;
  readonly text: string;              // the window, for search_query
  readonly tokenBudget: number;
}

export interface PeerRepresentation {
  readonly summary?: string;
  readonly card: readonly string[];        // stable biographical facts
  readonly conclusions: readonly string[]; // prose, with provenance
  readonly tokenUsage?: AiTokenUsage;      // feed /api/metrics
}

/** Narrative context about the owner. NOT structured memory. */
export interface PeerRepresentationPort {
  recall(query: RepresentationQuery): Promise<PeerRepresentation>;
  observe(window: ConversationWindow): Promise<void>;  // fire-and-forget
}

export const NoopPeerRepresentation: PeerRepresentationPort = { … };

Why this shape works:

  • It returns strings, not domain entities — an honest signal that this is narrative context, not structured memory. No pollution.
  • AssistantContextBuilder.renderGrounding() already composes five labelled sections. This becomes a sixth: "What Honcho concludes about the owner:". One function, one new section.
  • It carries tokenUsage, so Honcho's cost lands in /api/metrics alongside every other role — consistent with the MeteredEmbedding precedent from ADR-0011.
  • A Noop implementation means dry-run stays free, matching the whenUnset degradation pattern of all five existing model roles.
  • observe() is separate from recall() because writes are fire-and-forget and reads are on the critical path. Different failure semantics deserve different methods.
  • It obeys test/core-layer-portability.test.ts — no node:* in the port, transport lives in src/infrastructure/memory/honcho-*.ts.

Plugin, wrapper, or client?

You asked specifically. The answer is client, and the reason is not preference.

✗ Nocheh as a Hermes plugin

The blocker: Hermes's gateway flow is Platform event → authorize → resolve session → create AIAgent → run_conversation. The raw message is in the prompt and sent to the model inside that loop. A memory-provider plugin is called for reads and writes around the loop, not before it.

So your rule 2 — "redact before anything else" — becomes unenforceable. You cannot gate what you do not sequence. Everything else (Python, prompt ownership, cache stability as a stated design principle) is secondary to that.

✗ Nocheh as a wrapper around Hermes

You'd shell out to a large Python agent, then try to reconstruct structure from its free-text answers. You inherit its dependency tree, its provider resolution, its session storage, and its upgrade cadence.

In exchange you get tools you could add yourself in a fraction of the code. Wrapping something bigger than you to use a slice of it is how a clean architecture dies.

✓ Nocheh as a Honcho client

Exactly the relationship you already have with NVIDIA, Anthropic, Gemini and Notion MCP: a port in src/application/ports, an adapter in src/infrastructure, wired once in src/dev-server.ts.

Rule 7 already tells you to do this: "Providers stay behind ports. Transport in the adapter; prompt, output contract, and domain mapping stay shared." Honcho is a provider. Treat it like one.

One more asymmetry worth naming. Hermes's Honcho integration includes pinUserPeer, userPeerAliases, runtimePeerPrefix — an entire identity-mapping layer whose only job is to collapse Telegram/Discord/Slack runtime IDs onto the right Honcho peer, with a documented footgun about orphaning pooled memory when you flip pinUserPeer. Nocheh is single-owner. You get all of that complexity for free by not having it. Do not import a multi-tenant identity problem you do not have.

The guard — the thing that caught a photographed whiteboard password the perception model transcribed verbatim, per ADR-0010 — has not. Never write to Honcho above line 233.

  5. Wire recall() into AssistantContextBuilder

    Call it in parallel with retrieval.query() via Promise.allSettled. Add a sixth section to renderGrounding(). Extend the context_build audit metadata with honchoConclusionCount, honchoCardCount, honchoLatencyMs — you now have an A/B record for free, in a table you already query.

  6. Extend the contract by exactly one sentence

    ADR-0012 established the rule and pinned it with a test: tell the model what groundingContext is and forbid extracting from it. Honcho conclusions are inference, not testimony — the risk of a model minting a Decision node out of Honcho's guess is real. Extend analysisSystemPrompt() in memory-graph-analysis-mapping.ts:95 and update the token-budget assertion in test/memory-graph-analysis-mapping.test.ts.

  7. Backfill, explicitly

    POST /api/memory/rebuild-representation, mirroring POST /api/memory/reindex. ADR-0011's reasoning applies unchanged: it is paid work per record, so it is a deliberate button, not a startup side effect. Feed it guarded history through HistoryImportService's chunking, and return 409 when no Honcho credentials are configured — same as reindex does today.

  8. Measure, then decide

    Run 20–30 real windows with both paths active. Compare from /api/audit: did Honcho's conclusions reduce duplicate node creation? Did the graph get cleaner? Did context_build latency stay acceptable? If the answer is no, delete one adapter file and one wiring block. That reversibility is the whole reason to structure it this way.

Risks and the triggers that should change your mind

Risks of adopting Honcho

  • Two sources of truth. When the graph says one thing and a conclusion says another, which wins? Decide now: the graph is the record of fact; Honcho is advisory context. Encode it in the prompt.
  • Ops surface triples. SQLite file → Postgres + pgvector + Redis + worker. Backups, migrations, restarts.
  • Untestable dependency. You cannot pin its conclusions in a unit test. Contract-test the adapter, fake the service.
  • Vendor trajectory. AGPL core mitigates lock-in, but the hosted models (Neuromancer) are theirs. Self-hosting uses your LLM key and different models than their benchmarks measured.
  • Benchmarks aren't your corpus. LoCoMo and BEAM are English conversation datasets. Your corpus is mixed-language, media-derived, group-chat Telegram.
  • Privacy, if hosted. Guarded ≠ anonymous. Self-host.

Risks of not adopting it

  • You tune constants for weeks that someone else already tuned, and end up worse.
  • No consolidation path. The graph accretes. Contradictions accumulate. In two years, recall degrades and nothing in the design fixes it.
  • Persian recall stays half-blind — 25% of the blend is structurally zero, on embeddings whose floor is a guess.
  • Extraction-only ceiling. Your contract can only capture what a window says. Coaching needs what months of windows imply, and you have no step that produces it.
  • No fast read path. Nocheh can file things away but cannot answer you in under a second.

One page, if you read nothing else

  1. Honcho is a memory service. Hermes is a harness that calls Honcho. They are not alternatives to each other, and only one is a candidate for your app.
  2. Honcho is better than your recall layer. Not better than your graph — it deliberately refuses to build one and says so in its own docs.
  3. Hermes is not a memory solution. Its memory is markdown files plus FTS5. Its good memory is Honcho.
  4. Do not become a plugin. Inside Hermes's loop you cannot guarantee redaction runs first, and that is rule 2. Everything else is negotiable; that isn't.
  5. Do not wrap Hermes. Inheriting a large Python harness to use a slice of it trades your clean architecture for tools you could write yourself.
  6. Be a client. New port PeerRepresentationPort, new adapter, wired once in dev-server.ts. Exactly how you already treat NVIDIA, Gemini, Anthropic and Notion. Rule 7 already told you this.
  7. Self-host Honcho. A write to it is external sync. Hosted means your entire life corpus sits in someone else's plaintext Postgres, permanently.
  8. Insert at two points only: observe() after the guard at process-incoming-message.ts:233, recall() inside AssistantContextBuilder. Both additive, both non-fatal, both deletable in an hour.
  9. Never write to Honcho from the buffer. Only regex has run there. The guard is the gate, and it is load-bearing — it caught a password a perception model read off a photograph.
  10. Do option A first, for one week. You have one latency data point and zero live graph runs. Measure your recall before you replace it.
  11. Keep everything auditable, enumerable, and approvable in Nocheh. Graph, tasks, suggestions, external actions, audit, encryption. That is the product. Honcho is a better retrieval brain bolted to it — not a replacement for it.
  12. Mine Hermes for free. MIT-licensed. Take the cron design, the channel-adapter shapes, document extraction, and the draft/deliver split. Import none of it.
