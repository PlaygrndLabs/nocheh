# Architecture decisions

This page says which decisions hold today, grouped by area. Each bullet links the ADRs behind it.
Open an ADR only when you need its reasons, rejected options or exact limits.
ADR files are historical records and stay unchanged; a later ADR replaces only the parts it names.
[SPECS.md](../../SPECS.md) defines the product, [TASK.md](../../TASK.md) records status, and [AGENTS.md](../../AGENTS.md) holds the working rules. ADRs never override them. [CATALOG.md](CATALOG.md) is the full chronological index.

## Nocheh in one paragraph

Nocheh is a personal AI brain. It owns the original archive, the rules, the secret check and every owner decision. Hermes is the agent today, behind the agent socket: it runs each turn in a sealed container and returns the reply. Nocheh's own `nocheh-telegram` service is the Telegram bot that receives and sends messages. Telegram is one front door, not the product. Honcho is long-term memory, and Hermes native notes are a smaller per-chat memory. Inngest drives durable workflows, but Nocheh's own Postgres state decides each step. The runtime, the memory service, the model providers and the front door all sit behind adapters and can be swapped.

## Current decisions

### Product and ownership

- Nocheh is a personal AI brain, not a task bot; outward actions need owner approval ([0007](0007-personal-ai-brain-roadmap.md)).
- Nocheh owns the archive, rules, secret check, approvals and dashboard; Hermes is a replaceable runtime behind an adapter ([0018](0018-hermes-owned-archive-subscription-rebuild.md), [0027](0027-native-hermes-dashboard-integration.md)).
- Where Hermes or Honcho has a built-in, Nocheh uses it instead of its own copy and keeps its safety layer around it: the secret check, audience filtering and archive provenance ([0228](0228-hermes-and-honcho-built-ins-replace-nocheh-copies.md)).

### Archive and sources

- Three stores: the archive keeps originals only, the derived store keeps masked copies and generated material, and the control store keeps authority and operations state ([0053](0053-original-only-archive.md)).
- Data is plain text at rest, so it can be indexed and searched ([0014](0014-postgres-plaintext-at-rest-owner-column.md)).
- Sources have platform-independent identities, revisions and relations beside the unchanging event log ([0051](0051-platform-independent-sources.md)).
- Preparation turns media into text with Hermes tools: the document reader for files, the transcriber for voice notes and the vision tool for images ([0192](0192-files-are-read-by-the-runtime-document-reader.md), [0193](0193-voice-notes-are-transcribed-by-the-runtime-transcriber.md), [0194](0194-images-are-read-by-the-runtime-vision-tool.md)); a photo is read once, at its largest size ([0251](0251-fixes-that-lose-nothing.md)), and every recording is transcribed whole, whoever sent it: a group is read whole from everyone, and only members interact with the agent ([0264](0264-groups-are-read-whole-from-everyone.md)). The bytes are parsed by `nocheh-reader`, with no network and no key, each file in a process and login of its own that is ended and wiped after it; only text, or a PNG or Ogg it made again, comes back ([0285](0285-files-are-parsed-by-a-separate-reader.md)).
- The agent reads a chat oldest first through access checks, searches Honcho memory by meaning within readable sessions, and finds current reactions with masked excerpts ([0195](0195-the-agent-reads-a-chat-in-order-and-searches-by-meaning.md), [0084](0084-scoped-reaction-discovery.md), [0086](0086-reaction-discovery-evidence.md)).
- Every chat has Nocheh's own id that never changes: a chat value stored before step 2b stays as its chat's id, a chat first seen later gets a digest of its app ids with no bot in it, and each app id a chat has had, current or old, maps to it. Code asks the chat directory what a chat is, never an id's shape; an id it does not know is private and reads nothing. Archive reads expand chats to their app ids at query time, with no event index, and the owner's private chat is kept apart from the owner's account ([0252](0252-chats-get-nochehs-own-ids.md)).

### Secret check and security

- The secret check is on or off. When on, preparation stores a masked copy of each source as a guard revision that the owner can edit ([0033](0033-guarded-projections-and-honcho-memory.md)).
- Every Hermes model request passes the Hermes request boundary and the nocheh-security service, which owns policy, brokered provider calls and effect decisions; Honcho's model requests are checked by Nocheh through Honcho's provider gateway; a required check fails closed ([0020](0020-mandatory-outgoing-request-guard.md), [0037](0037-external-security-plugin-service.md)).
- A model-list request with no content, or with only a numeric page size, passes unchecked ([0172](0172-provider-model-lists-pass-the-guard.md), [0179](0179-anthropic-model-list-page-size-passes-the-guard.md)).
- Checks run side by side, three by default; reply checks take free slots before background checks; one audience's runtime context is masked side by side ([0127](0127-parallel-guard-checks.md), [0137](0137-side-by-side-runtime-context-guarding.md), [0139](0139-reply-checks-before-background-checks.md)).
- Identical text reuses one detector result across audiences and guard epochs; a first transcript or extraction choice does not start a new epoch ([0138](0138-shared-context-detection.md), [0170](0170-secret-check-results-survive-guard-epochs.md), [0108](0108-first-derivative-selection-does-not-revoke.md)); a finding from a batch of several texts reaches another audience only when a check of that text alone confirms it, and an AI finding never masks object keys or a model request's roles, types, names, model or tool ids ([0251](0251-fixes-that-lose-nothing.md)).
- Text the check declines twice on its own is masked whole as a secret ([0184](0184-text-the-secret-check-always-declines-is-hidden.md)).
- Hermes runs with a read-only root, a memory `/tmp`, no capabilities and only the folders it writes mounted; a read that fails for a full `/tmp` or a refused write reaches the owner; its own pages carry script rules, report-only until a week without reports ([0251](0251-fixes-that-lose-nothing.md)).

### Telegram and other doors

- In a group Nocheh serves, the owner and the members who talk there start turns. Members live in the control store and are managed on the Members page: each has a pause, "Talk to Nocheh in groups they joined" with small jobs, posts to their other groups and web pages and outside tools under it, tasks read and write or read only, and a switch per group that counts as on until the owner turns it off. A change applies at once, with no restart and no guard epoch, and each effect checks the member again just before it happens; a decision made without a message from the group also needs Telegram to show them in it ([0260](0260-members-in-groups.md), replacing [0062](0062-owner-managed-telegram-group-participants.md)).
- A member also talks to Nocheh in their own private chat while they are active and their "Private chat with Nocheh" is on, also with group talk off. It only reads: that chat, and the groups they joined that Telegram showed them in within 30 days (asked again before a private turn when older than 6 hours, then older ones in the places left, at most 10; groups past the cap are left out of that turn and its tools), with those groups' whole history and their projects' tasks one project at a time. Its reads are bound on the server for every request, it gets no notes tool, no own role, no shared or granted context and no effect, and its turns share the daily message cap and one lane per member with their group turns, taken before the group's, so a member's waiting turn never holds up the owner's there ([0262](0262-member-private-chat.md)). It also reads, with no card, the Notion and linked GitHub repositories of each active project holding a group it reads, sharing or not; anything that would ask is refused and not kept. A schedule's run reads Notion and GitHub where its chat may, with no card; its changes still ask ([0278](0278-member-private-chat-reads-project-connectors.md)).
- The owner's turns never read a member's private chat or any private chat that is not the owner's, and owner recall skips member profiles. When the owner's own, not forwarded, message names a member and asks what they said, one read-only turn answers from that chat alone, in a separate never-learned `member_read` message that is then dropped ([0262](0262-member-private-chat.md)).
- A member also has the members' app, opened from the menu button every private chat with Nocheh has: a page at `/m/` on the mini app's address whose calls `nocheh-miniapp` forwards only to its own listener in `nocheh-app` (port 8790, never the dashboard or the owner's routes, on an internal network the edge shares only with the dashboard and the app). Telegram's signed launch data names the member on every call, for at most an hour, with no password; only an active member gets in, checked in SQL on each call, anyone else gets one closed answer, and a launch from before an add, an un-pause or a sign-out is refused. It shows the boards of the projects that hold groups the member joined, confirmed by Telegram within 6 hours, each task only as its board shows it; with Tasks read and write the member adds, changes, finishes, comments on, trashes and restores any task they see, never deletes for good, and sets reminders to themselves. The page is in English only, and every project view shows a person assigned only while they are in a group of the project, counting the rest, never the owner's names for people ([0265](0265-member-mini-app.md)). Each board is its project's whole list, whatever each task's group and whatever "Share group chats" says, and names the project's groups for its labels and filter ([0276](0276-a-projects-tasks-are-one-list.md)).
- The owner's Telegram user ID is never a member; the owner sets it once in Settings › Telegram, and later it changes only from the command line ([0244](0244-owner-defaults-posts-and-machine-reports-stay-private.md), [0260](0260-members-in-groups.md)).
- By default a group message starts a turn only when it addresses Nocheh: it replies to or mentions the bot, or opens with its display name or a name in `TELEGRAM_BOT_NAMES`; `TELEGRAM_GROUP_REPLIES=all` answers every message ([0133](0133-group-replies-when-addressed.md), [0134](0134-editable-bot-names.md)).
- Chats Nocheh does not serve are archived but never prepared or shown to a model; a private stranger, or a member who is paused or has private chat off, gets one fixed reply a day ([0182](0182-strangers-cost-nothing-and-reach-no-model.md), [0262](0262-member-private-chat.md)); a member's own open private chat is prepared and answered. In a served group, a stranger, or a member who is paused or may not talk there, gets one fixed reply a UTC day per group, and a member over the daily message cap gets one cap reply a day there ([0260](0260-members-in-groups.md)).
- Every physical send is re-checked against its approved chat, topic and current policy; a rate-limited send gets at most three journaled attempts, and an uncertain send never resends ([0089](0089-physical-telegram-delivery-boundary.md), [0090](0090-durable-telegram-rate-limit-retries.md)).
- Hermes shows typing while a turn works and reacts on the answered message: eyes while working, then thumbs up or down ([0188](0188-typing-status-while-a-turn-works.md), [0211](0211-hermes-working-reactions-on-the-answered-message.md)).
- Every request a front door sends to a chat app, reactions included, leaves one content-free send record (kind, chat, when, outcome and a code), drained into `control.chat_sends` and shown in System › Sent to apps, on Health and in the owner's notices; "typing…" and reads never; a record never decides a send ([0238](0238-record-every-send-to-a-chat-app.md)).
- A Telegram turn's pass is bound to where its chat is in Telegram (`{app, chat, topic}`); storage, the bot and Hermes refuse a pass that does not match, and only the Telegram front door translates Nocheh chats to Telegram ids, so a group Telegram upgrades stays the same chat and sends follow it. The bot and Hermes read the served chats from the app ([0252](0252-chats-get-nochehs-own-ids.md)).
- Only the owner adds Nocheh to a group, and a group is on only while its chat record says so; no setting lists groups. The owner's add turns it on at once, and a card in the owner's private chat then puts it in a new project of its own, with Move to, No project and Turn off. When anyone else adds Nocheh, it leaves and keeps a content-free record; a member's or an anonymous admin's add also sends the owner one line, within daily caps. A group Nocheh is in with no add on record stays Off and silent and is never left on its own, and removal from a group that was on sends one line. The owner turns a group on or off in Chats at once, and turning one off keeps its members' switches ([0253](0253-only-the-owner-adds-nocheh.md), [0260](0260-members-in-groups.md)).

### Replies and turns

- Nocheh's own bot polls and sends for Telegram ([0235](0235-nocheh-owns-the-telegram-bot.md)); each chat has its own Hermes profile with a fixed tool set and its own role (SOUL.md) and skills; a role or skill change reaches continuing sessions through Hermes' own prompt refresh ([0021](0021-scoped-native-assistant-processes.md), [0151](0151-chat-role-and-skills-in-hermes-profiles.md), [0228](0228-hermes-and-honcho-built-ins-replace-nocheh-copies.md)).
- The owner's private chat and groups each have their own default role and skills; only the owner's private chat takes its default, and every other turn takes the default for groups, which starts empty ([0244](0244-owner-defaults-posts-and-machine-reports-stay-private.md)).
- Each turn runs in its own sealed container, and abandoned leases are reclaimed under the profile lock ([0028](0028-isolated-native-browser-turns.md), [0098](0098-isolated-native-lease-recovery.md)).
- The dashboard has no chat page until Nocheh has its own: Hermes's chat page, its WebSocket and the browser input routes are refused, so a browser never reaches the agent as the owner. Hermes has no mount of stored files and reads a turn's images through the broker with the turn's pass, and it reads a pass's claims without checking the master key's signature; Nocheh's own services still check it ([0289](0289-chat-page-off-and-hermes-reads-passes-without-the-master-key.md)).
- Turns start in Telegram update order per chat or topic; chats and topics run in parallel up to owner limits (3 replies, 4 agent runs) ([0104](0104-telegram-update-order-and-untransmitted-sends.md), [0125](0125-per-chat-telegram-dispatch-lanes.md), [0136](0136-per-topic-dispatch-lanes.md), [0126](0126-owner-set-parallel-replies-and-runs.md)).
- The owner's instruction texts ride on each runtime call; defaults stay in code ([0152](0152-owner-editable-built-in-instructions.md)).
- A group turn also sees up to 20 recent unaddressed messages, masked and cited; an album gets one turn on its first part ([0157](0157-group-turns-see-recent-unaddressed-messages.md), [0155](0155-albums-answered-once.md)).
- A group message from the owner carries a `[the owner]` tag on its speaker line, so replies speak to the owner directly ([0222](0222-a-group-turn-knows-when-the-owner-speaks.md)).
- A new guard epoch's profile starts with the recent conversation, and old profiles are removed after 15 idle minutes, whether the chat was last opened from Telegram or the dashboard ([0163](0163-chat-conversation-carries-into-new-guard-epochs.md), [0168](0168-superseded-epoch-profiles-are-removed.md), [0227](0227-hermes-lists-chats-by-their-names.md)).

### Honcho memory

- Long-term memory sits behind a memory socket; Nocheh keeps receipts, sessions, sharing rules and deletions, and Honcho is the only engine plugged in today ([0232](0232-memory-engine-socket.md)).
- Honcho is primary long-term memory, on by default in fresh installs, run in the installation Compose project and attached once at startup; Nocheh is its only writer, and Hermes has no direct access ([0033](0033-guarded-projections-and-honcho-memory.md), [0045](0045-honcho-in-installation-compose.md), [0076](0076-honcho-enabled-local-default.md), [0061](0061-retire-isolated-honcho-comparison.md)).
- One workspace per installation, stable peers for people and projects, and versioned sessions per conversation; Nocheh enforces audience on every read ([0056](0056-connected-entity-memory.md), [0109](0109-standard-honcho-entity-model.md), [0115](0115-honcho-session-revisions.md)); Honcho peer cards are off and Nocheh reads none ([0225](0225-member-safety-rules.md)).
- Repeat names for one person or project wait on one suggestion card that learning or the owner folds them into; one answer covers every name ([0219](0219-repeat-names-wait-on-one-card.md)).
- A reply reads its conversation's Honcho session context live when a message arrives, and context is prefetched when Honcho finishes work, never on a timer ([0044](0044-automatic-honcho-context.md), [0114](0114-event-driven-honcho-context.md), [0115](0115-honcho-session-revisions.md)).
- Only the latest revision of an edited message stays in Honcho; only an uncorrected owner change or a replaced session pauses reads, and answering a suggestion card or renaming a person does not ([0154](0154-message-edits-replace-honcho-writes.md), [0148](0148-honcho-reads-wait-for-epoch-correction.md), [0149](0149-only-owner-changes-hold-honcho.md), [0223](0223-answering-a-suggestion-card-does-not-pause-memory.md)).
- Memory evidence shows the exact messages Honcho records a conclusion citing, else its derivation batch marked inexact ([0228](0228-hermes-and-honcho-built-ins-replace-nocheh-copies.md)).
- Limited, syncing or paused memory reaches the agent as context; Nocheh adds no text to a reply about it ([0221](0221-limited-memory-is-context-not-reply-text.md)).
- Honcho's model may call only the tools its request offered; the gateway refuses any other, so a group's memory reads stay in the group's sessions ([0241](0241-honcho-runs-only-the-tools-it-offered.md)).
- A group's recall, search and learning ask read through a memory wall: a Honcho named scope of exactly the chats its recall reads, named by those chats, opened with its own key, so memory itself refuses anything outside it. A member's private chat and a private answer search through the wall of their groups, with no learned notes. Private chats are never in a wall; the owner and session context read as before. Honcho runs with auth on, keyed by the internal token ([0286](0286-memory-walls.md)).
- Every Honcho call to its provider gateway names its memory workspace; the vector reconciler retries each workspace's pending embeddings with that workspace named, in requests the gateway accepts, and a call with none is refused ([0259](0259-honcho-retries-each-workspace-bound.md)).
- Historical recall needs evidence beyond the current question; terminal queue errors block readiness; preparation outages answer 503 so Honcho retries; recall checks run at reply priority ([0099](0099-independent-evidence-for-historical-recall.md), [0101](0101-honcho-terminal-queue-errors-block-readiness.md), [0174](0174-memory-preparation-outages-are-retried.md), [0150](0150-honcho-recall-checks-take-reply-priority.md)).
- The owner can retry learning, re-learn chosen chats or start a fresh workspace; changing the memory search model rebuilds memory; a 30-minute synthetic workspace allows checks while memory is detached ([0153](0153-owner-reruns-and-replaces-honcho-memory.md), [0122](0122-honcho-fresh-start.md), [0181](0181-memory-search-model-change-rebuilds-memory.md), [0068](0068-detached-honcho-acceptance-workspace.md)).
- Other people's forwards and the text of files and audio are written by one peer that is not a person, `nocheh_forwards_and_files`: in the owner's private chat a forward goes to its own session, which owner turns read as a separate block, and in a group to that group's session, so neither shapes what is known about the owner; each new record names its source in fixed words, and a claim resting on a forward, a file or someone else's message is reported or inferred, never direct. Data written before keeps its form ([0257](0257-learned-memory-names-its-source.md)).
- Honcho reads a learned note as what it is: the owner's correction or a rule people set is kept as a fact within its scope, anything else as Nocheh's inference; a note is dated by the message that set off its learning, else its latest evidence, and an owner's correction by when the owner made it, never by when it is written to Honcho, so a re-learn does not move it to the re-learn day ([0275](0275-honcho-3-6-2-and-reading-instructions.md), [0280](0280-learned-notes-keep-their-date-and-kind.md)).

### Hermes native notes and learning

- Each live source gets at most one native notes review, run in a supervised thread outside workflow admission, after Honcho ingestion's first attempt ([0097](0097-durable-native-review-handoff.md), [0124](0124-native-review-once-per-source.md), [0088](0088-primary-ingestion-before-native-note-review.md)).
- A review that failed or timed out without changing notes, or whose start Hermes never recorded (lost or refused before it began), runs again, up to four attempts ([0183](0183-failed-native-review-without-effect-runs-again.md), [0185](0185-review-stopped-at-its-time-limit-runs-again.md), [0258](0258-a-notes-review-whose-start-was-lost-waits-again.md)).
- A review runs as one Nocheh asked for, so it may change or remove notes to make room; no note write waits for an approval no one can give ([0239](0239-notes-reviews-make-room-in-full-notes.md)).
- A review's input budget is 48,000 prompt tokens, cached or not: room on full notes for more than one write and the answer ([0240](0240-notes-reviews-get-room-to-retry-on-full-notes.md)).
- Waiting reviews, including failed ones waiting to run again, keep their place and an open workflow across epochs; stopped learning is asked again, and stranded work is picked up at start ([0173](0173-waiting-native-reviews-keep-their-place.md), [0216](0216-failed-reviews-keep-their-place-across-epochs.md), [0217](0217-waiting-fragments-keep-their-place.md), [0176](0176-stopped-learning-is-asked-again.md), [0177](0177-stranded-memory-work-is-picked-up-at-start.md)).
- Learning asks Honcho questions of up to 92,160 bytes, about half of Honcho's input budget sized to the guard's 512 KiB, and gets schema-checked JSON from Honcho's structured output; it keeps valid items and reuses results unless real evidence changes ([0128](0128-learning-results-keep-valid-items.md), [0228](0228-hermes-and-honcho-built-ins-replace-nocheh-copies.md), [0082](0082-evidence-based-learning-deduplication.md)).
- Automatic publication waits while a reply is active; privacy revocations apply at once ([0083](0083-defer-automatic-memory-publication-during-replies.md)).
- A retired source leaves Hermes history and notes: history rows become notices naming the retired ID, and notes citing it are removed; a message a turn quoted as a group's recent message or as the message it replied to leaves as its own notice, and that turn's tool work and notes go with it, while the turn's message and answer stay; a stored row that cites a record of facts resting on a retired message is withheld too, and the fact no longer opens ([0123](0123-retired-sources-leave-native-history.md), [0132](0132-retired-history-placeholders.md), [0129](0129-retired-sources-leave-native-notes.md), [0261](0261-recalled-facts-and-search-hits-name-their-source.md)).
- Each message Nocheh sends carries a send class. Its cards, card updates, refusals, notices and reminders are kept and stay context for the owner's reply, but are not learned unless the owner turns learning on for one; replies, follow-ups, private answers, job reports, scheduled results and approved posts are learned ([0256](0256-nochehs-own-messages-carry-a-send-class.md)). Nothing in a private chat that is not the owner's, and no `member_read` answer, is ever learned, granted or suggested, whatever the owner says ([0262](0262-member-private-chat.md)).
- A message from someone not allowed where they wrote (anyone but the owner and the members who talk there, [0260](0260-members-in-groups.md)) stays out of the owner's notes, and only there, for the rest of the installation generation. Each note carries a label code builds from Nocheh's own record of who wrote it: "you" only for a review of nothing but the owner's own messages that cites them, never for a turn's note. The model reads it in fixed words beside the unchanged note, and the owner in editable words in Memory › Assistant notes ([0257](0257-learned-memory-names-its-source.md)).

### Audience and sharing

- Owner recall spans every chat Nocheh serves; each group has its own memory audience, and its topics share it unless `TELEGRAM_TOPIC_MEMORY=topic` ([0030](0030-configurable-space-memory.md), [0135](0135-group-topics-share-memory.md)); each recalled note names the chat it came from, and the sharing filter's model sees only the search words, never the question ([0251](0251-fixes-that-lose-nothing.md)).
- Each search hit and opened message names who wrote it, where and when, in a tag Nocheh's code builds from the archive and the reader's own copy, with `by` saying whose words they are; a reader never learns from a tag anything it may not read (another group, the owner's private chat, a People name, a topic name only the owner typed, the owner's time zone). Opening a message also shows what it replies to and its replies, each only where the reader may read it ([0261](0261-recalled-facts-and-search-hits-name-their-source.md)).
- Each long-term memory fact a turn or `memory_recall` reads sits under a source line code builds from the messages Honcho learned it from, with the time of its message; the observed person's own message comes first, so a fact about Bob that cites the owner's question names Bob, and `by=owner` only when every source is the owner's own typing. A fact opens with `archive_read nocheh:memory:<id> fact=<n>`, only in the reader's own audience, never once a source is retired or memory no longer holds it ([0261](0261-recalled-facts-and-search-hits-name-their-source.md)).
- A turn whose message replies to another reads that message first, named the same way, with up to 200 characters of its text, and each recent group message says what it replies to without its text; a message in a forum topic is no reply to the topic's opening. A note written after reading a message its turn replied to says so, unless the owner typed that message; a review's label names its day, and each note in a turn opens what it was written from with `archive_read note=<ref>` in that turn only ([0261](0261-recalled-facts-and-search-hits-name-their-source.md)).
- The owner's dashboard shows where messages and facts came from, in the owner's own words: in Messages a message's thread (a forum topic's first message is its topic, never what it replies to) and the facts long-term memory learned from it; in Memory › Long-term the facts it learned, newest first, by chat or person, with their messages and how many name them exactly; in Notes a note's day and the messages it was written from; and a short label beside every linked message. A retired message is never linked, and a label that can't be read shows no link ([0261](0261-recalled-facts-and-search-hits-name-their-source.md)).
- Relationships never grant access; the owner approves one-time or lasting fact grants per group or topic ([0057](0057-memory-relationship-access-map.md)); a project never grants access in a group: a group answer uses only that group, and the owner's own sharing rules and fact grants are the one exception ([0247](0247-projects-replace-the-share-box.md)).
- A grant, its follow-up message and its workflow request commit together; delivery re-checks the exact grant; replays are serialized and keep expiry; an unstarted handoff resumes on an exact owner replay ([0093](0093-atomic-memory-approval-followups.md), [0094](0094-current-memory-authority-at-delivery.md), [0095](0095-recover-unstarted-memory-handoffs.md), [0096](0096-serialize-memory-decision-replays.md)).
- Only groups and their topics share, are shared with or join a project; every other chat, the owner's included, counts as private and fails closed. Suggestions skip facts with private evidence, one-time access posts once now, lasting access posts only when chosen, and every share names where the fact came from and who will see it ([0242](0242-private-chats-stay-out-of-group-sharing.md)).
- The full tester plants private marks in the owner's private chat (a message, a note, a personal task, a private job, the owner's role), checks that no group's or project chat's model request or answer holds one, and sweeps everything the fake Telegram sent outside the owner's chat; Notion and the mini app are unit-checked ([0244](0244-owner-defaults-posts-and-machine-reports-stay-private.md)); every answer of the members' app and every reminder sent to a member's chat are swept for marks too ([0265](0265-member-mini-app.md)).
- "Answer privately", under the owner's own answer in a group or topic of a project that has another served group, answers the same question in the asker's private chat. ## How to add or interpret an ADR

- Use SPECS.md for the intended product and TASK.md for what is built or active.
- Add an ADR only for a lasting architecture choice whose reasons will matter later. ADRs are not progress logs.
- Name exactly which earlier decision the new one extends or replaces. Do not retire a whole ADR when one boundary changed.
- Add the new ADR to [CATALOG.md](CATALOG.md) and to the right area on this page; move replaced decisions to "Replaced decisions".
- Never edit an accepted ADR. Fix SPECS.md, this page, the catalog, or write a new ADR instead.
